## قبل تجربة الإدارة المركزية للمigrations

- تطبيق أحدث Platform PostgreSQL migration على قاعدة Platform.
- تشغيل RabbitMQ وPlatform API وPlatform Worker وSchools API.
- تم التحقق محليًا من اكتمال Action المدرسة وتحول `MigrationStatus` إلى `Succeeded` وتحديث `SchemaVersion` إلى `20260917214728_AddSchoolFacilities` بعد تشغيل Worker وconsumer.
- تجربة حالة فشل آمنة والتأكد من تسجيل `LastMigrationError` وإمكانية إعادة المحاولة.

## تحسينات قريبة

- نقص مؤكد أثناء توثيق المرحلة السابعة: قصر إغلاق التقويم ويوم الحضور Daily على `BranchId` غير مطبق في ResolveContext رغم حفظ الفرع في الإعداد. بعد طلب التنفيذ، تحديد فرع الفصل الفعلي وقواعد كل الفروع/الفرع الخاص، وربط الحدث واليوم بالنطاق الصحيح، ثم اختبارات عدة فروع ونقل غرفة/عدم وجود إسناد. الدليل يحذر من الاعتماد على إغلاق فرع منفرد أو اختلاف أيام الفروع حاليًا؛ لم يعدل التطبيق أو البيانات.

- اكتمل تنفيذ مقترحي التكليف التشغيلي وتعدد مسجلي الحضور بعد موافقة المستخدم 2026-10-05؛ التفعيل والاختبار على قاعدة فعلية موضحان أعلى هذا الملف.
- مقترح بانتظار اعتماد المستخدم: استكمال إشعارات إلغاء/نقل إسنادات المدرس وتغيير المكان، الرئاسة والتنسيق، اعتماد خطط التدريس، وتذكيرات الأعمال غير المكتملة؛ يليها متابعة الطلاب وتغييرات قوائم الفصول والأنشطة وطلبات التقديم. يحدد كل حدث المستلم الفعلي ورابطه ومنع التكرار والتجميع والتصعيد، دون إضافة Family إلى نطاق المدرسة.
- Smoke test فعلي متعدد الحسابات لإشعارات إسناد المدرس: قسم/مادة صف/فصل/حصة أساسية ومرشح بديل، حفظ متكرر وإعادة إسناد وتغيير وقت، منع إنشاء إشعار عند فشل الحفظ، فتح الروابط دون صلاحية إدارة، وفتح إشعار قديم بعد إزالة الربط. لم تُعدّل قاعدة مدرسية فعلية خلال التنفيذ؛ Push/Realtime يظلان عملًا مستقلًا.
- تطبيق migrations `AddExamWorkflowNotifications` على قواعد المدارس وإعادة تشغيل Schools API، وضبط `ExamWorkflow:SchoolCodes` من إعداد النشر غير السري، ثم smoke test بعدة مستخدمين: تجهيز/مراجعات متوازية/اعتماد/نشر، منع غير المسؤول والإجراء القديم، الإرجاع وإعادة الإسناد، تعديل الموعد والإلغاء، التذكير والتصعيد. لم يُنفذ الاختبار على قاعدة مدرسة فعلية حتى الآن.
- ربط مستهلك ExamNotificationOutbox بقناة Push/Realtime مع retry ومراقبة delivery مستقبلًا؛ الإشعارات الداخلية محفوظة الآن لكن لم يُنفذ Push جديد. يظل Family والإرسال للإدارة التعليمية خارج النطاق.

- تطبيق migrations `AddSchoolPresentation` على قواعد المدارس القائمة من Action التحديث المركزي، ثم تجديد جلسة المدير لإظهار `school.profile.manage` وتجربة رفع الشعار والصور وحفظ التعريف واختيار الغلاف وإزالة صورة الغلاف وتعارض تحريرين. ضبط `SchoolDocuments__StorageRoot` على volume دائم. العرض العام وFamily غير داخلين في التنفيذ الحالي.
- تطبيق migrations `AddTeachingPlansAndDocumentCore` على قواعد المدارس القائمة، وضبط `SchoolDocuments__StorageRoot` على volume دائم، ثم smoke test فعلي للإنشاء متعدد الفصول والاعتماد والنشر ومنع التداخل ورفع/تنزيل المرفق.
- توصيل `ISchoolDocumentStorage` بمزود S3/MinIO في الإنتاج وإضافة فاحص malware يحدّث `SchoolDocumentValidationStatus`، ثم إضافة روابط typed تدريجيًا للواجبات والأنشطة والملاحظات وإصدارات الكتب.
- تطبيق migrations `AddSchoolClassActivities` على قواعد المدارس القائمة من Action التحديث المركزي، ثم smoke test بمدرسة فعلية يغطي المسودة والنشر والجمهور المحدد ومزامنة قيد جديد والحفظ الجزئي والإكمال والإلغاء وإعادة الفتح.
- إضافة optimistic concurrency صريحة لتعديل مسودة النشاط وتقييم المشاركين، حتى يعاد conflict واضح بدل last-write-wins إذا عدّل مستخدمان نفس النشاط أو الطالب بالتزامن.
- توحيد استهلاك access token المتجدد في Flutter عبر authenticated client أو session provider مشترك، بحيث تستفيد الصفحات المدفوعة المفتوحة طويلًا من التجديد دون الحاجة إلى الرجوع وإعادة فتحها.
- تطبيق Schools migration `AddSchoolHomework` على قواعد المدارس القائمة من Action التحديث المركزي، ثم إجراء smoke test ببيانات مدرسة فعلية لإنشاء Online/Offline بدرجة إجمالية، والتحقق من رفض اختلاف مجموع أسئلة الأونلاين، ثم نشره وتقييم تسليم أوفلاين، مع تغطية نموذج متعدد الاختيارات والفراغات وتعديل المسودة وعرض التفاصيل. يبقى Family API/UI وإشعارات الأسرة وGradebook مؤجلة لمراحلها المستقلة.
- إضافة تقارير الحضور اليومية/حسب الحصة، ملخصات التأخير والانصراف المبكر، وإشعارات أولياء الأمور عند بدء Family App.
- استكمال دورة Admissions المتقدمة بالمقابلات والمرفقات والتدقيق والتواصل والإشعارات، ثم استقبال مصدر `FamilyApp` على نفس كيان الطلب دون نقل قواعد القبول خارج Schools Backend.
- ربط الخطة اليومية بخانة الجدول وكيان `LessonDelivery` عند بدء مرحلة تنفيذ الدروس، دون دمج التحضير بسجل التنفيذ الفعلي.
- تطبيق Schools migrations `AddSchoolExamCore` ثم `AddSchoolExamOperations` ثم `RefineSchoolExamPeriodsAndScopes` على قواعد المدارس القائمة من Action التحديث المركزي، وإجراء smoke test فعلي يغطي المداخل الثلاثة، اشتقاق اختبار التيرم/نهاية العام، كشف تداخل الشهري، إنشاء سلسلة متعددة المواد، لجنة وسعتها ومراقبًا وبديله، النشر والتوزيع، الحضور والنتائج والتظلم وتقرير CSV.
- لاحقًا عند بدء Family App فقط: إضافة جدول الطالب والأسرة، عرض النتيجة المنشورة، تقديم التظلم وإشعارات الأسرة. لا يُضاف هذا السطح إلى Schools Web أو Schools Flutter.
- ربط نتائج الاختبارات بوحدة Gradebook عند تصميمها، مع استهلاك النتيجة المنشورة و`ResultsRevision` بدل تكرار منطق الرصد داخل Gradebook.
- عند تنفيذ HR: تحويل مصدر سجلات الإذن والغياب والإجازة من الإدخال اليدوي المرحلي إلى وحدة HR عبر `SourceType/SourceReferenceId` وintegration events، مع إبقاء `TeacherSubstitution` كتغطية أكاديمية مؤرخة.
- بعد اكتمال النظام الأكاديمي: تفصيل النظام المالي المدرسي إلى Domains الرسوم والتحصيل والمحاسبة والمشتريات والموازنات، وتفصيل الإدارة الداخلية إلى Employee Core والعقود والحضور والإجازات والرواتب والأصول والمخزون.
- عند بدء Family App: تنفيذ حسابات الأسرة والطالب وربطهم بالمدرسة وطلبات التقديم ومواعيد المقابلات والمحاضرات الأونلاين والتواصل، مع إبقاء قواعد العمل ومصدر الحقيقة داخل Backend.
- استخدام مرجع Ultimate Schools عند تفصيل نطاق `Student Core` و`Guardians` و`Admission and Enrollment`، وتحديث المرجع عند اكتشاف وظائف جديدة أو اكتمال فجوة داخل Mdaresna.
- تطبيق أحدث Schools migration `AddSchoolCurriculumBooks` على قواعد المدارس من Action التحديث المركزي حتى تظهر وحدة المواد والمناهج والكتب في المدارس الموجودة.
- ربط إشعارات المدرسة الحالية بقناة Firebase/Realtime لإرسال Push لحظي، مع بقاء School Notifications API والتخزين الحاليين مصدر الحقيقة.
- عرض حالة آخر migration وإصدار قاعدة المدرسة داخل شاشة المدارس بدل الاكتفاء برسالة قبول الطلب.
- إضافة polling أو notification للواجهة عند اكتمال عملية migration asynchronous.
- إضافة معالجة إدارية للعمليات التي تبقى `Pending` مدة طويلة، مع retry آمن ومراقب.
- إضافة integration tests تشمل RabbitMQ ومسار command/result كاملًا.
