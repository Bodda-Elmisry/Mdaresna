# القرارات المعمارية

آخر تحديث: 2026-09-17

## ADR-001 — قاعدة بيانات مستقلة لكل مدرسة

- الحالة: معتمد.
- القرار: لكل مدرسة قاعدة تشغيلية مستقلة، بينما Platform يحتفظ بالـregistry والبيانات الإدارية المشتركة.
- السبب: العزل بين المدارس، سهولة النقل والاستعادة، ودعم خيارات نشر مستقبلية.
- الأثر: أي عملية School تحتاج أولًا إلى تحديد المدرسة ثم حل database endpoint الخاص بها.

## ADR-002 — Platform يدير Registry ولا ينفذ منطق المدرسة

- الحالة: معتمد.
- القرار: Platform يحتفظ بـ`school_database_endpoints` ويصدر أوامر الإدارة، بينما Schools هو المسؤول عن إنشاء وتشغيل قاعدة المدرسة.
- السبب: فصل Control Plane عن Tenant Data Plane وعدم تحميل Platform API مسؤولية الاتصال المباشر بكل قواعد المدارس.

## ADR-003 — الفصل بين Person وLocalUser

- الحالة: معتمد.
- القرار: `Person` يمثل الشخص داخل المدرسة، و`LocalUser` يمثل الشخص القادر على تسجيل الدخول.
- السبب: الطالب قد يكون Person بدون حساب، بينما المدرس أو الموظف أو المدير يمكن ربطه بحساب محلي.

## ADR-004 — بيانات دخول محلية للمدرسة

- الحالة: معتمد.
- القرار: تسجيل الدخول يكون بـ`username@schoolCode`، ثم يستخدم school code لحل قاعدة المدرسة ويُتحقق من username وكلمة المرور داخلها.
- السبب: الحفاظ على عزل credentials لكل Tenant مع استخدام اسم دخول كامل وفريد للمستخدم.

## ADR-005 — OTP عند طلب التفعيل وليس أثناء provisioning

- الحالة: معتمد.
- القرار: رسالة اكتمال إنشاء المدرسة تحتوي اسم الدخول فقط. OTP يُولد عند محاولة التفعيل الأولى، ثم يحدد المستخدم كلمة المرور.
- السبب: تقليل صلاحية الأكواد غير المستخدمة وتوحيد السلوك مع دعوات الموظفين.

## ADR-006 — migrations المدارس من Platform فقط

- الحالة: معتمد.
- القرار: المدارس الجديدة تشغل migrations أثناء provisioning، والمدارس الموجودة تُحدّث عبر Action مركزي في Platform.
- مرفوض: تشغيل `MigrateAsync()` عند كل Request أو Login أو طلب OTP.
- السبب: تجنب locks وtimeouts والتشغيل المتوازي، وتوفير سجل مركزي للنجاح والفشل.
- التنفيذ: Outbox → RabbitMQ → Schools migration consumer → result event → Platform Worker.

## ADR-007 — صلاحية مستقلة لتحديث قواعد المدارس

- الحالة: معتمد.
- القرار: استخدام `platform.schools.migrations.execute` وعدم ربط التنفيذ بصلاحية القراءة أو التفعيل.
- السبب: migration عملية تشغيلية عالية التأثير ويجب منحها بشكل صريح. يحصل `App Manager` عليها تلقائيًا من migration بيانات Platform.

## ADR-008 — إدارة الأسرار في النشر

- الحالة: معتمد.
- القرار: user-secrets للتطوير المحلي فقط، وenvironment variables أو secret manager داخل Docker/Cloud.
- السبب: user-secrets ليست آلية نشر ولا تُنسخ تلقائيًا للحاويات.

## ADR-009 — ربط مستخدم المدرسة بالهوية المركزية عن طريق الهاتف الرئيسي

- الحالة: معتمد.
- القرار: عند إضافة مدرس أو موظف يبحث Schools عبر Platform internal API عن Identity account بواسطة رقم الهاتف الرئيسي؛ ينشئ الحساب المركزي عند عدم وجوده، ثم يخزن `PlatformAccountId` داخل المستخدم المحلي.
- إذا كان الرقم موجودًا كرقم غير رئيسي يُرفض الطلب بدل إنشاء حساب مكرر أو إرسال الرسالة إلى جهة اتصال ثانوية.
- الحساب وكلمة المرور والأدوار تظل محلية داخل قاعدة المدرسة، بينما Identity المركزية مسؤولة عن هوية الشخص ورقم الهاتف المستخدم لإرسال الدعوة وOTP.
- حذف المستخدم من مدرسة يحذف السجل المحلي فقط ولا يحذف Identity account المشترك.

## ADR-010 — حماية الإدارة المحلية للمدرسة

- الحالة: معتمد.
- القرار: يجب أن يبقى داخل كل مدرسة موظف `Employee` فعال واحد على الأقل يحمل دور النظام `School Admin`.
- تمنع إدارة المستخدمين تعديل الحساب الحالي أو تعطيله أو حذفه؛ الملف الشخصي هو المسار المخصص لتعديل بيانات المستخدم نفسه.
- حماية آخر مدير تشمل إزالة الدور، تغيير النوع إلى `Teacher`، التعطيل، والحذف، وتُطبق داخل Schools API وليس في الواجهة فقط.

## ADR-011 — جهات اتصال مستخدم المدرسة الإضافية

- الحالة: معتمد.
- القرار: مصدر الهاتف الرئيسي هو Identity Database ويُقرأ من Schools عبر Platform internal API وقت تحميل الملف الشخصي. تُقرأ جهات الاتصال الإضافية من قاعدة المدرسة داخل `person_contacts` وتُدمج مع الهاتف الرئيسي في الاستجابة.
- أي نسخ رئيسية قديمة داخل قاعدة المدرسة لا تدخل في استجابة جهات الاتصال؛ جهة الاتصال الرئيسية القادمة من Identity غير قابلة للتعديل أو الحذف من إعدادات المدرسة، بينما يمكن إدارة الهاتف والبريد والعنوان الإضافيين محليًا.
- جهات الاتصال الإضافية بيانات ملف شخصي فقط ولا تصبح معرّفات تسجيل دخول؛ تعديل الهاتف الرئيسي يظل من خلال إدارة الهوية المركزية.
