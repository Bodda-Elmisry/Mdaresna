# الحالة الحالية للمشروع

آخر تحديث: 2026-09-26

## مستودعات تطبيقات الواجهات

- تطبيقات الواجهات الأربعة محفوظة في مستودعات GitHub مستقلة على فرع `main`: `mdaresna-platform-web`, `mdaresna-schools-web`, `mdaresna-platform-flutter`, و`mdaresna-schools-flutter` تحت حساب `Bodda-Elmisry`.
- مستودعا الويب يحتويان Dockerfile وإعداد runtime عبر `/env.js`، بينما مستودعا Flutter يستبعدان ملفات Firebase المحلية ومواد توقيع التطبيقات وملفات البيئة من Git.

## المراجع التنافسية الدائمة

- المرجع الوظيفي الدائم لمنصة Ultimate Schools محفوظ في `docs/reports/ULTIMATE_SCHOOLS_REFERENCE.md`، ويجمع نتائج فحص إعداد المدرسة والطلاب والجداول والحضور والتقييم والامتحانات والنتائج والبوابات، مع مقارنة Mdaresna وترتيب التنفيذ المقترح.
- التقرير المنسق المقابل محفوظ في `docs/reports/Mdaresna-UltimateSchools-Academic-Gap-Analysis-AR.docx`.
- النطاق المستقبلي المتفق عليه للنظام المالي والإدارة الداخلية للموظفين والموارد وFamily App محفوظ في `docs/reports/POST_ACADEMIC_MODULES_REFERENCE.md`.
- لا تُخزن بيانات دخول المنصة المرجعية أو أي أسرار داخل ملفات المشروع.

## حدود الوحدات المستقبلية

- بعد اكتمال النظام الأكاديمي، تُنفذ داخل نطاق المدرسة وحدات النظام المالي وإدارة الموظفين والموارد، وتظل بياناتها التشغيلية داخل قاعدة المدرسة.
- Family App هو قناة الطالب وولي الأمر للتقديم وربط الأسرة والمواعيد والمقابلات والمحاضرات الأونلاين والتواصل وعرض البيانات الأكاديمية والمالية المسموح بها.
- Family App لا يملك قواعد القبول أو القيد أو الحضور أو الدرجات أو الرسوم؛ تظل قواعد العمل ومصدر الحقيقة في Schools Backend والوحدات المركزية المناسبة للهوية والإشعارات.

## التطبيقات

- `Mdaresna`: Backend ويحتوي Platform API وPlatform Worker وSchools API والعقود المشتركة.
- `Mdaresna_Platform_Web`: تطبيق إدارة المنصة باستخدام React.
- `Mdaresna_Platform`: تطبيق إدارة المنصة باستخدام Flutter.
- `Mdaresna_Schools_Web`: تطبيق المدارس باستخدام React.
- `Mdaresna_Schools`: تطبيق المدارس باستخدام Flutter.

## تعدد المدارس وقواعد البيانات

- كل مدرسة تمثل Tenant ولها قاعدة بيانات تشغيلية مستقلة حاليًا.
- Platform هو Control Plane ويحتفظ ببيانات المدرسة وموقع قاعدة بياناتها داخل `registry.school_database_endpoints`.
- لا تُخزن بيانات الاعتماد داخل السجل؛ يستخدم `CredentialSecretReference` للإشارة إلى مصدر أسرار خارجي.
- PostgreSQL هو المزود الافتراضي الحالي لقواعد المدارس.
- إنشاء مدرسة جديدة يشغل أحدث Schools migrations أثناء provisioning قبل تفعيل المدرسة.
- تحديث قواعد المدارس الموجودة يتم مركزيًا من Platform فقط، وليس أثناء تسجيل الدخول أو مع كل Request.

## دورة إنشاء المدرسة

1. المستخدم يرسل طلب إنشاء مدرسة من Schools Web أو Flutter.
2. Schools ينشر event إلى RabbitMQ.
3. Platform يستهلك الطلب، يتحقق من حساب المالك أو ينشئه، ويسجل المدرسة بحالة انتظار المراجعة.
4. مسؤول Platform يقبل المدرسة ويختار نوع الوحدة.
5. Platform ينشر أمر provisioning.
6. Schools API consumer ينشئ قاعدة PostgreSQL، يشغل migrations، يضيف معلومات المدرسة، وينشئ المستخدم المحلي للمالك بحالة انتظار التفعيل.
7. Schools يعيد نتيجة provisioning؛ Platform يسجل database endpoint ويفعّل المدرسة.
8. المالك يستلم رسالة باسم الدخول الكامل فقط، بدون OTP.

## هوية مستخدم المدرسة

- `Person`: الشخص داخل نطاق المدرسة، وقد يكون طالبًا أو مستخدمًا.
- `LocalUser`: شخص يستطيع تسجيل الدخول إلى تطبيق المدرسة مثل المالك أو المدير أو الموظف أو المدرس.
- بيانات الدخول محلية داخل قاعدة المدرسة وليست Platform credentials.
- صيغة الدخول: `username@schoolCode` مع كلمة مرور المدرسة المحلية.
- التفعيل لأول مرة: يطلب المستخدم OTP بعد إدخال اسم الدخول، ثم يرسل OTP وكلمة المرور الجديدة.
- OTP لا يُنشأ ولا يُرسل أثناء provisioning.
- دور `School Admin` والصلاحيات المحلية والأدوار وعلاقات المستخدمين موجودة على مستوى قاعدة المدرسة.
- Schools Web يحتفظ بجلسة تسجيل الدخول ويستخدم access token لقراءة بيانات المدرسة المحلية.
- Platform وSchools يدعمان «تذكرني» في Web وFlutter. الـaccess token قصير العمر ويُجدد قبل انتهائه بدقيقة باستخدام refresh token دوّار؛ يستعيد العميل الجلسة عند التشغيل أو يعيد شاشة الدخول إذا انتهت أو أُلغيت.
- زر تسجيل الدخول في Schools Web وFlutter يعرض حالة انتظار مترجمة ويمنع الإرسال المتكرر حتى اكتمال الطلب، وكذلك إجراءات التفعيل.
- جلسة «تذكرني» صالحة حتى 30 يومًا، والجلسة غير الدائمة حتى يوم واحد. Web يستخدم `localStorage` للدائمة و`sessionStorage` لغير الدائمة، بينما Flutter يحفظ الجلسة الدائمة فقط في التخزين الآمن للنظام عبر `flutter_secure_storage` ولا يحفظ كلمة المرور.
- تسجيل الخروج يلغي refresh token في الـBackend ويمسح التخزين المحلي. Platform يستخدم جدول `identity.sessions` الموجود، وSchools يستخدم `local_user_sessions` داخل قاعدة المدرسة، لذلك لم تُضف migrations لهذه الميزة.
- يلغي Platform فحص JWT بهدوء إذا أُلغي طلب HTTP نفسه أثناء فتح اتصال قاعدة البيانات، ولا يصنف هذا كتوكن غير صالح؛ تظل أعطال PostgreSQL الحقيقية غير مخفية.
- `GET /api/schools/v1/school-profile` يعيد بيانات `SchoolInformation` للمدرسة المحددة من claim كود المدرسة.
- لوحة Schools Web تعرض اسم المدرسة الفعلي، وصفحة بيانات المدرسة تعرض بياناتها بدل النص التجريبي.
- قائمتا الحساب والإشعارات في Schools Web تتبعان نفس نمط Platform Web؛ الحساب يحتوي هوية المستخدم والأدوار واللغة وتسجيل الخروج، والإشعارات تعرض empty state لحين إضافة School Notifications API.
- إعدادات Schools Web مقسمة إلى بيانات شخصية وأدوار؛ الملف الشخصي وتخزين الصورة محليان داخل قاعدة المدرسة، وإدارة الأدوار محكومة بصلاحيتي `school.roles.view` و`school.roles.manage`.
- البيانات الشخصية في Schools Web تجلب الهاتف الرئيسي مباشرة من Identity عبر Platform internal API، وتدمجه مع الهاتف والبريد والعنوان الإضافيين المخزنين في `school.person_contacts`؛ الهاتف الرئيسي يظهر للقراءة فقط ولا تستخدم الجهات الإضافية لتسجيل الدخول.
- تبويبا «المعلمين» و«الموظفين» موجودان داخل الإعدادات لإدارة الحسابات والأدوار والحالات ونطاق مواد المعلم. العرض والإدارة محكومان بصلاحيتي `school.users.view` و`school.users.manage`.
- Schools Web يعرض أيضًا شاشتين تشغيليتين مستقلتين في القائمة الرئيسية بلا إضافة أو تعديل أو إيقاف أو حذف للحساب. تعرضان الصورة والهوية والقسم والحالة، وتدعمان التصفية المستقلة بالقسم والاسم ورقم الهاتف؛ وتحتوي شاشة المعلمين على التفاصيل والجدول الأسبوعي، وتحتوي الشاشتان على تسجيل الغياب والإذن والإجازة يدويًا.
- شاشة «الفصول» التشغيلية موجودة في القائمة الجانبية على Web وFlutter. يرى `School Admin` كل الفصول النشطة، ويرى المدرس فقط الفصول المرتبطة به عبر إسناد مادة داخل الفصل؛ ويطبق Schools API هذا النطاق قبل إعادة البيانات. تعرض الشاشة المسار الأكاديمي والفترة والسعة والإشغال والغرفة والمواد المتاحة للمستخدم.
- نطاق بيانات الشاشتين مُطبق في Schools API: `School Admin` يرى كل المعلمين والموظفين؛ وغيره يرى نفسه والأعضاء الفعالين في الأقسام التي يقودها والأقسام التابعة لها فقط، مع بقاء RBAC شرطًا مستقلًا. نفس النطاق يحمي الصورة والتفاصيل والتعديل وتغيير الحالة والحذف ونطاق التدريس وجدول المعلم.
- تصفية المستخدمين تتم Server-side؛ تستخدم الإعدادات البحث العام والحالة والدور، بينما تستخدم الشاشات التشغيلية القسم والاسم والهاتف، وتدخل كل الفلاتر في الإجمالي والـpagination.
- الحساب الحالي لا يمكن تعديله أو تعطيله أو حذفه من شاشة إدارة المستخدمين؛ تعديلات بياناته الشخصية تتم من تبويب البيانات الشخصية.
- يجب أن يوجد دائمًا موظف `Employee` فعال واحد على الأقل يحمل دور `School Admin`؛ تمنع الـAPI إزالة دوره أو تحويله إلى مدرس أو تعطيله أو حذفه إن كان الأخير.
- إنشاء مدرس أو موظف يبدأ بحل رقم الهاتف الرئيسي داخل Identity المركزية؛ إن لم يوجد الحساب يُنشأ، ثم يُنشأ `Person` و`LocalUser` داخل قاعدة المدرسة بحالة `PendingActivation` وتُرسل رسالة باسم الدخول الكامل `username@schoolCode`.
- مسار OTP وتعيين كلمة المرور لأول مرة متاح لكل مستخدم مدرسة في حالة انتظار التفعيل، وليس مقصورًا على مالك المدرسة؛ وبعد نجاحه يؤكد Schools للـPlatform أن الهاتف الرئيسي تم التحقق منه لتفعيل Identity account المعلق.
- صور مستخدمي المدرسة محفوظة في `school.person_profile_images` ومقيدة بصيغ JPEG/PNG/WebP وحجم 2 MB.
- المستخدم الذي لديه صورة يعرضها جدول المستخدمين عبر endpoint محمي بصلاحية `school.users.view`، مع fallback لأيقونة المستخدم.

## الطلاب وطلبات التقديم

- الـPlatform هو مصدر كود الطالب العالمي: يحتفظ بـ`GlobalStudentRegistry` ويصدر `GlobalStudentId` وكود `STU-*` فريدًا عبر internal API محمية. لا يحتفظ بقيد الطالب أو عضويته في مدرسة.
- كل قاعدة مدرسة تحتفظ بملف الطالب المحلي ونسخة مفهرسة من الهوية والكود العالمي، وأولياء الأمور، والقيود الدراسية، وطلبات التقديم. يرتبط الطالب بـ`Person` محلي واحد وفريد ويمكن ربط أكثر من ولي أمر به مع أساسي واحد إلزامي.
- تدعم المدرسة مسارين: تسجيل طالب مقيد مباشرة داخل فصل، أو إنشاء طلب تقديم يدوي بمصدر `SchoolDesk` ثم قبوله لاحقًا؛ القبول ينشئ الطالب والقيد ويربطهما بالطلب، ويخصص الكود العالمي عند الحاجة.
- شاشتا Schools Web وSchools Flutter تعرضان تبويبي «طلاب المدرسة» و«الطلبات المقدمة» بصلاحيات مستقلة. البحث Server-side بالعام ونوع التعليم والمرحلة والصف والاسم والكود وتاريخ الميلاد؛ يضيف الطلاب الفصل والحالة، وتضيف الطلبات الحالة والمصدر ونطاق تاريخ التقديم دون فلتر فصل قبل القبول. تعرض Schools Web هذه الحقول داخل لوحة عوامل تصفية collapsible مغلقة افتراضيًا ومتسقة مع Platform Web.
- يملك كل سجل طالب Action لعرض التفاصيل في Web وFlutter؛ يعرض البيانات الأساسية والرسمية، جميع أولياء الأمور وخصائص كل علاقة، وسجل القيود الدراسية التاريخي كاملًا.
- الصلاحيات هي `school.students.view/manage` و`school.admissions.view/manage`، ويحصل عليها `School Admin` من seed قاعدة المدرسة.
- migrations الحالية: Platform SQL Server `20260925191826_AddGlobalStudentRegistry` وPostgreSQL `20260925191837_AddGlobalStudentRegistry`؛ Schools PostgreSQL `20260925193625_AddStudentCoreAdmissions` وSQL Server `20260925193637_AddStudentCoreAdmissions`.

## تحديث قواعد بيانات المدارس

- الصلاحية: `platform.schools.migrations.execute`.
- يوجد Action لمدرسة واحدة وAction لكل المدارس الفعالة في Platform Web وPlatform Flutter.
- Platform API يسجل العملية كـ`Pending` ويكتب الأمر في Outbox ثم يرجع HTTP 202.
- Platform Worker ينشر الأمر إلى RabbitMQ.
- Schools migration consumer يتحقق من tenant/database target ويشغل `Database.MigrateAsync()`.
- النتيجة تعود إلى Platform Worker ويتم تحديث `MigrationStatus`, `SchemaVersion`, operation id، التواريخ، وآخر خطأ.
- الحالات الحالية: `NeverRun`, `Pending`, `Succeeded`, `Failed`.
- إذا كان RabbitMQ أو consumer متوقفًا تبقى الرسالة في Outbox/Queue وتُستكمل بعد عودة الخدمة.
- يلزم تشغيل Platform Worker لنشر أوامر Outbox واستهلاك نتيجة migration؛ تشغيل Platform API وSchools API وحدهما غير كافٍ.
- Platform Web يعرض عدد عمليات تحديث الكل التي دخلت الطابور فعليًا، ويحذر إذا كان العدد صفرًا بسبب عدم وجود مدارس مؤهلة أو وجود عملية معلقة، ويعرض رسالة واضحة للعملية الفردية الجارية.

## الإعدادات المدرسية

- الهيكل التنظيمي الموحد منفذ في Schools API وSchools Web وSchools Flutter: قسم بنوع `Academic` أو `Administrative` ونطاق على مستوى المدرسة أو فرع، مع شجرة أقسام اختيارية وترتيب وحالة تشغيل وsoft delete واستعادة.
- عضوية القسم مؤرخة وتسمح بعضويات ثانوية مع قسم أساسي واحد فقط لكل مستخدم. رئاسة القسم علاقة مؤرخة منفصلة، ويجب أن يكون الرئيس عضوًا فعالًا داخل القسم.
- القسم التعليمي يمكن ربطه بعدة مواد، ولكل مادة منسق مع نطاق اختياري لنوع تعليم ومرحلة؛ المنسق يجب أن يكون مدرسًا وعضوًا بالقسم. القسم الإداري لا يقبل المواد أو المنسقين، لكن نوع القسم يوجه مرشحي الواجهة ولا يمنع الاستثناءات التنظيمية في العضوية.
- الهيكل التنظيمي مستقل عن RBAC ولا تمنح العضوية أو الرئاسة صلاحيات تقنية تلقائيًا. الصلاحيات هي `school.departments.view/manage/delete/restore` ويحصل عليها `School Admin` من seed البيانات.
- صفحة الإعداد الأكاديمي في Schools Web تعرض الهيكلة الأكاديمية والصفوف الدراسية والمواد والمناهج وجدول الحصص داخل Accordion أحادي الفتح؛ أول قسم مفتوح افتراضيًا، وفتح قسم يغلق السابق، ولا تُحمّل بيانات القسم المقفول حتى فتحه.
- الهيكلة المادية منفذة في Schools API وSchools Web وSchools Flutter، وتعرض الإعدادات حسب الاعتماد: فرع ← مبنى ← دور ← أنواع الغرف ← قدرات الغرف ← الغرف؛ ويمكن للغرفة امتلاك عدة قدرات تسمح مثلًا لمعمل واحد بدعم الكيمياء والفيزياء.
- الهيكلة المادية تدعم CRUD، التفعيل والإيقاف، soft delete، سلة المحذوفات والاستعادة، وتمنع حذف الأصل قبل نقل أو حذف الأبناء.
- الصلاحيات: `school.facilities.view`, `school.facilities.manage`, `school.facilities.delete`, `school.facilities.restore`، ويحصل عليها `School Admin` من seed البيانات.
- الهيكلة الأكاديمية منفذة في Schools API وSchools Web وSchools Flutter: نوع تعليم ← تعريف عام دراسي ← عام للبرنامج ← تيرمات ← فترات، مع CRUD والتفعيل والإيقاف وsoft delete والاستعادة.
- التنظيم الدراسي داخل نوع التعليم منفذ كالتالي: مرحلة دراسية ← مسار اختياري ← صف دراسي، ثم فتح الصف داخل عام البرنامج وإنشاء فصل دراسي واحد أو أكثر له. تشغيل الصف يحفظ فقط مرجعي العام والصف والسعة والحالة؛ الكود والاسمان يولدهم Schools API تلقائيًا، والمرحلة والمسار مجرد فلاتر اختيار في الواجهة.
- الفصل الدراسي كيان سنوي مستقل عن الغرفة المادية؛ نموذج إنشائه يطلب تشغيل الصف والسعة والفترة فقط، ويولد Schools API الكود والاسم التسلسلي تلقائيًا. ربط الفصل بالغرفة يتم من خلال إسناد مؤرخ اختياري الساعات، مع التحقق أن نوع الغرفة مخصص للفصول وأنها قابلة للجدولة وسعتها كافية ولا يوجد تعارض زمني.
- يظهر تشغيل الصف في حالتي `Draft` و`Active` عند إنشاء الفصل ويُمنع استخدام `Closed` أو المحذوف؛ لا يمكن تفعيل صف مفتوح قبل وجود فصل دراسي فعال واحد على الأقل، ولا يمكن بعد تفعيله تعطيل/حذف/نقل آخر فصل فعال منه.
- التقويم والتشغيل منفذان بقوالب أيام ومواعيد الدراسة القابلة للتخصيص حسب نوع التعليم والفرع، وأحداث التقويم والإجازات والإغلاق والأنشطة والاختبارات القابلة للربط بنوع التعليم والعام والفرع.
- الصلاحيات المستقلة هي `school.academics.*`, `school.operations.*`, `school.calendar.*` (`view/manage/delete/restore`) ويحصل عليها `School Admin` من seed البيانات.
- نوع الغرفة يحتوي `IsClassroom` لتمييز الغرف الصالحة لإسناد الفصول، ولا يمكن إلغاء هذا الوصف أو تقليل السعة/الجدولة بما يكسر إسنادًا فعالًا.
- وحدة المواد والمناهج والكتب منفذة في Schools API وSchools Web وSchools Flutter: تعريف مادة مشتركة، خطة منهج ذات إصدار مرتبطة بنوع التعليم، توزيع المادة على الصف داخل الخطة، كتاب وإصدار كتاب، وأدوار كتب seeded (`PRIMARY`, `WORKBOOK`, `TEACHER_GUIDE`, `SUPPLEMENTARY`, `REFERENCE`, `ACTIVITY_BOOK`).
- `ProgramAcademicYear` يحدد `CurriculumPlan` الفعالة لنوع التعليم، ولا يمكن تغيير الإسناد بعد بدء العام. يسمح للعام القديم الذي بدأ بلا خطة بإسناد أول خطة مرة واحدة لدعم الترقية، ثم يُقفل. قبل تفعيل الخطة تُراجع نواقص مواد الصفوف والكتب والكتاب الأساسي وتُعرض للمستخدم؛ يمكن التفعيل رغمها بموافقة صريحة، وبعد التفعيل تصبح التفاصيل وإصدارات الكتب snapshot تاريخية غير قابلة للتعديل.
- `GradeSubjectOffering` يمثل التشغيل السنوي الفعلي لمادة الخطة داخل `GradeOffering`، ولا يقبل الربط إلا عندما يتطابق الصف والخطة المثبتة على عام البرنامج.
- نطاق تدريس المدرس منفذ عبر `TeacherGradeSubjectScope` على مستوى مادة صف محددة داخل عام محدد؛ المرحلة ونوع التعليم مجرد فلاتر في الواجهة ولا يسندان كل صفوف المرحلة تلقائيًا.
- قائمة المدرسين في Schools Web تحتوي Action «المواد والصفوف» لاختيار العام ونوع التعليم والمرحلة ثم صفوف ومواد مستقلة.
- قائمة المدرسين والموظفين في Schools Web تحتوي Action «عرض التفاصيل» يفتح ملخصًا موحدًا للهوية والصورة والحالة والبيانات الشخصية وجهات الاتصال والأدوار؛ ويضيف للمدرس نطاق الصفوف والمواد وإسنادات الفصول الحالية ودوره ومواعيد حصصه. الهاتف الرئيسي يُقرأ من Identity عند فتح التفاصيل وباقي الجهات من قاعدة المدرسة.
- سجل الفصل في Schools Web وSchools Flutter يحتوي Action «مدرسو الفصل»: تختار مادة مشغلة في صف الفصل ثم عدة مدرسين مؤهلين لها عبر `TeacherGradeSubjectScope`. تحفظ الاختيارات في `ClassSectionTeacherScope`، وتظهر في تفاصيل المدرس، ولا تحدد الأساسي أو البديل إلا لاحقًا من جدول الحصص.
- جدول الحصص الأسبوعي منفذ في Schools API وSchools Web وSchools Flutter كمصفوفة مستقلة لكل فصل: نوع التعليم كتبويبات، والمرحلة كلوحة أحادية الفتح، ثم الصف/العام والفصول. إعداد المرحلة يحفظ `DailyLessonCount` و`DailyBreakCount`، ويكون عدد أعمدة اليوم مجموعهما، بينما يحدد المستخدم داخل كل خلية هل هي حصة أم فسحة وتوقيتها.
- أيام جدول الحصص النشطة تُعرض دائمًا بترتيب أسبوع مدرسي صريح: السبت، الأحد، الاثنين، الثلاثاء، الأربعاء، الخميس، الجمعة؛ وتُخفى الأيام غير المعرفة في مواعيد دراسة نوع التعليم، بينما يستخدم الجدول الأسبوع الكامل إذا لم توجد إعدادات أيام بعد.
- خلية الحصة تحفظ المادة والمدرس الأساسي وقائمة اختيارية من صفر أو عدة مدرسين بدلاء، وكلهم مقصورون على `ClassSectionTeacherScope` للمادة نفسها. تمنع الـAPI تساوي الأساسي مع أي بديل وتكرار البدلاء، ولا تفحص تعارض البديل إلا عند الإسناد الفعلي مستقبلًا؛ وتستمر في فحص تعارض الفصل والمدرس الأساسي والحد الأسبوعي للمادة والحد اليومي للفسح.
- قائمة المدرسين في Schools Web وSchools Flutter تحتوي Action «عرض الجدول» يجمع حصص المدرس الأساسية من جميع الفصول، ويعرض أيضًا التغطيات الفعلية المؤرخة المسندة إليه مع المادة والفصل والوقت واسم المدرس الغائب. المرشح البديل لا يظهر كحصة فعلية إلا بعد حفظ `TeacherSubstitution` له.
- خلية الحصة الأسبوعية ترث تلقائيًا الغرفة الأساسية المسندة للفصل خلال العام الدراسي، ولذلك تظهر حصص الفصل في جدول غرفته بدون إعادة اختيارها. اختيار غرفة مختلفة داخل الخلية يمثل نقل الحصة أو استخدامها معملًا. الحجز المشترك اختياري وصريح، ولا يقبل التداخل إلا إذا كانت كل الحجوزات المتداخلة مشتركة وكان مجموع سعات الفصول داخل سعة الغرفة. تعرض Schools Web جدول الغرفة الأسبوعي وفيه المادة والفصل والصف والمدرس والحجوزات المشتركة.
- الدمج المؤقت للفصول منفذ كسجل تشغيلي مؤرخ مستقل عن تعريف الفصل والجدول الأسبوعي: يختار غرفة وتاريخًا ووقتًا وفصلين أو أكثر والحضور المتوقع وملاحظات. تتحقق الـAPI من سعة الغرفة بحسب الحضور المتوقع ومن تعارض الغرفة أو الفصول، وتنفذ الإلغاء كـsoft delete.
- `WeeklyTimetableSlot` مرتبط مباشرة بالفصل وله `SlotNumber` و`IsBreak`، وتُحفظ قائمة البدلاء في `WeeklyTimetableSlotSubstituteTeacher`. لا يمكن حذف مدرس من فريق الفصل أو تعطيل حسابه إذا كان مستخدمًا كأساسي أو بديل، ولا يمكن تقليل حدود المرحلة بما يجعل خانات حالية خارج المدى. migrations للمزودين تنقل الجداول السابقة إلى التصميم الجديد وتعمل backfill للفصل ورقم الخانة والأساسي والبدلاء.
- `StaffAbsence` يسجل مبدئيًا غياب أو إذن أو إجازة المعلم والموظف يدويًا من شاشتي التشغيل، مع فترة تاريخية ووقت اختياري وملاحظات ومنع التداخل. تخضع القراءة والتعديل لنطاق القسم وصلاحيتي `school.people.view/manage`.
- تغطية غياب المعلم منفذة من سجل الغياب نفسه في Schools Web وSchools Flutter: تستخرج الحصص الفعلية الواقعة داخل مدة الغياب، وتتيح اختيار أحد البدلاء المرشحين في قالب الحصة. تحفظ النتيجة في `TeacherSubstitution` بتاريخ الحصة دون تغيير `WeeklyTimetableSlot`، وتمنع تعارض البديل أو اختياره أثناء غيابه. حذف سجل الغياب يلغي التغطيات المرتبطة به.
- يحمل كل من `StaffAbsence` و`TeacherSubstitution` حقلي `SourceType` و`SourceReferenceId` حتى تستبدل وحدة HR المستقبلية الإدخال اليدوي كمصدر رسمي دون إعادة تصميم التغطية الأكاديمية.
- وقت المدرسة التشغيلي مصدره `SchoolInformation.TimeZoneId` بصيغة IANA، وتحوّل Schools API وقت UTC الحالي عبر `SchoolClock` قبل اتخاذ قرار اليوم الدراسي أو الحصة الجارية. لا يعتمد الحضور على ساعة العميل أو موقع السيرفر، وتحفظ السجلات snapshot للمنطقة الزمنية.
- حضور الطلاب منفذ بسياسة `Daily` أو `PerSession` مع default للمدرسة وoverride لنوع التعليم ثم المرحلة. النمط اليومي يسجل مرة واحدة للفصل واليوم الدراسي، ونمط الحصة يسجل للحصة الجارية غير الفسحة فقط بواسطة المدرس الأساسي أو البديل الفعلي المؤرخ، مع نطاق كامل لـSchool Admin.
- شاشة الفصول في Web وFlutter تحتوي «فتح الفصل» ومساحة تشغيل بتبويبات الحضور والواجبات والأنشطة والاختبارات والملاحظات وتقييم الحصة. الحضور فعلي حاليًا: الطلاب حاضرون افتراضيًا، الحفظ يعتمد نتيجة لكل قيد فعال ويقفل السجل، والتصحيح يتم بإعادة فتح مدققة.
- جداول `student_attendance_registers/entries/audits` تمنع تكرار الفصل والتاريخ والوحدة وتحتفظ بهوية المسجل والمعتمد وحالة كل طالب. الصلاحيات هي `school.attendance.view/record/reopen`، والمigrations هي PostgreSQL `20260925213520_AddStudentAttendanceOperations` وSQL Server `20260925213557_AddStudentAttendanceOperations`.
- تبويب الواجبات داخل «فتح الفصل» منفذ في Schools API وSchools Web وSchools Flutter. يعرض للمدرس مواد الفصل المسندة إليه فقط، بينما يرى `School Admin` كل مواد الفصل، ويستطيع المستخدم المصرح له إنشاء واجب `Online` أو `Offline` مرتبط بمادة وكتاب اختياري وموعد تسليم حسب المنطقة الزمنية للمدرسة.
- كل واجب Online أو Offline يحمل `TotalScore` مطلوبًا ومستقلًا ضمن بياناته الأساسية. في الأونلاين يجب أن يساوي مجموع درجات الأسئلة وإلا ترفضه الواجهة والـAPI، بينما يستخدم الأوفلاين الإجمالي مباشرة في التقييم. يدعم الـQuestion Builder `SingleChoice`, `MultipleChoice`, `Text`, `FillInBlank` مع عدد اختيارات ديناميكي من 2 إلى 20 وعدة فراغات مستقلة لسؤال الإكمال، ولكل فراغ درجته وإجاباته المقبولة. يعمل المحرر في نافذة مستقلة عن بيانات الواجب في Web وFlutter، ويمكن عرض تفاصيل أي واجب وتعديل بيانات ونموذج المسودة فقط. بعد النشر تصبح الأسئلة ثابتة، وينشئ النظام snapshot من القيود الفعالة مع Action صريح لمزامنة الطلاب الذين أضيفوا لاحقًا.
- دورة الواجب المدرسية تدعم المسودة والنشر والإغلاق والإلغاء، قائمة حالة الطلاب، وتسجيل استلام ودرجة وتعليق الواجب الأوفلاين. يحفظ `homework_audits` الإنشاء والتعديل والنشر وتغيير الحالة ومزامنة الطلاب والتقييم والإعفاء.
- كيانات المحاولات والإجابات والاختيارات وإجابات الفراغات موجودة من البداية لدعم التسليم الأونلاين والتصحيح الآلي/اليدوي لاحقًا دون إعادة تصميم، لكن Family API وFamily App غير منفذين حاليًا حسب النطاق المعتمد.
- الصلاحيات المستقلة هي `school.homework.view/manage/publish/grade` ويحصل عليها `School Admin` من seed. migrations هي PostgreSQL `20260926132602_AddSchoolHomework` وSQL Server `20260926132640_AddSchoolHomework`.
- أخطاء Schools API تظل معرفة بأكواد مستقرة؛ Schools Web وSchools Flutter يترجمان الأكواد وفق اللغة النشطة ويستخدمان fallback مترجمًا بدل إظهار النص الإنجليزي القادم من الخادم. أخطاء تشغيل المواد تميز تحديدًا بين عدم إسناد الخطة للعام واختلاف الخطة أو الصف وعدم التفعيل.
- كيانات الهيكلة المادية تدعم حالتي التشغيل `Active/Inactive` بالإضافة إلى soft delete قابل للاستعادة؛ السجلات المحذوفة لا تظهر افتراضيًا ولا تُحذف ماديًا.

## الإشعارات

- Schools API يحفظ إشعارات المستخدم المدرسية داخل قاعدة المدرسة ويعيد آخر 50 إشعارًا مع عدد غير المقروء، ويدعم تعليم إشعار واحد أو الجميع كمقروء.
- إسناد تغطية حصة يرسل للبديل إشعارًا عربيًا وإنجليزيًا بالمادة والفصل والتاريخ والوقت واسم المدرس الغائب؛ تغيير التكليف أو إلغاؤه أو حذف الغياب يرسل إشعار إلغاء للبديل السابق.
- Schools Web يعرض العداد والقائمة السريعة وصفحة الإشعارات، وSchools Flutter يعرض صفحة الإشعارات والعداد وحالات القراءة. توصيل Push عبر Firebase/Realtime لم ينفذ بعد؛ التخزين داخل التطبيق هو مصدر الحقيقة الحالي.
- الإشعارات التي تحمل refresh signal تحدث حالة التطبيق فور وصولها في الواجهة الأمامية.
- العداد يتجدد من listener الاستقبال بدل الاعتماد على فتح قائمة الإشعارات.
- Web يطلب notification permission عند بدء التطبيق ويدعم browser notifications.
- إشعار تفعيل مستخدم Platform الجديد يوجه إلى قائمة المستخدمين ولا يجبر التطبيق على refresh كامل.

## إعدادات النشر الحساسة

- توجد Dockerfiles مستقلة لـPlatform API وPlatform Web وSchools API وSchools Web وPlatform Worker، مع `docker-compose.yml` موحد يضيف PostgreSQL وRabbitMQ وhealth checks وruntime environment configuration لتطبيقي الويب. دليل التشغيل في `docs/deployment/DOCKER_DEPLOYMENT.md`.
- لا تستخدم `dotnet user-secrets` داخل Docker أو بيئة الإنتاج.
- الأسرار تُمرر كـenvironment variables أو من secret manager.
- `PlatformSms__EncryptionKey` يجب أن تكون القيمة نفسها في Platform API وPlatform Worker.
- إعدادات PostgreSQL وRabbitMQ وFirebase وSMS وInternal API key يجب إدراجها في خطة النشر بدون تسجيل قيمها في المستودع.
