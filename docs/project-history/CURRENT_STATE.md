## School Social داخل المدرسة

- تحميل المنشورات والتعليقات paginated من API نفسه بنمط cursor/keyset حسب Id تنازلي (الأحدث أولًا): المنشورات 15 افتراضيًا والتعليقات 20 لكل دفعة، والحد الأقصى 50. يرسل العميل `before` ويقرأ `nextCursor`؛ Web/Flutter يحملان التالي عند الاقتراب من نهاية القائمة، مع زر «تحميل المزيد» ودمج دون تكرار. لا تُجلب كل السجلات مرة واحدة. تأكد ذلك بمراجعة التنفيذ في نقاش 2026-10-05؛ لا تغيير كود في هذه المراجعة.

- نافذة التعليقات في Web/Flutter تعرض خانة الإنشاء/التعديل أولًا ثم التعليقات المحملة بالتمرير. كارت التعليق يضم قائمة ثلاث نقاط رأسية بإجراءات وأيقونات تعديل/حذف/إبلاغ حسب صلاحياته الحالية، مع إلغاء التعديل؛ لا تغيير API أو Family. التحقق: Flutter analyze نظيف و26/26 tests، وفحص Web mock أكد موضع النموذج وفتح القائمة وإغلاقها عند اختيار التعديل وتركيز خانة الكتابة.

- أزرار تحميل/إعادة محاولة عرض الوسائط في معرض Web الداكن لها ألوان صريحة عالية التباين، لمنع وراثة النص الأبيض فوق خلفية زر بيضاء؛ زر التنزيل يحتفظ بمظهر ثانوي. لا تغيير لسلوك التحميل أو API.

- بطاقات الفيديو في قائمة المنشورات Web/Flutter تعرض أيقونة تشغيل مصممة وحجم الملف، دون توليد thumbnails أو تحميل الفيديو تلقائيًا. الضغط يفتح المعرض الموحد؛ تحميل/تشغيل الفيديو وتنزيله إجراءات يطلبها المستخدم داخله. Web ينزّل blob المصادق عليه ويعيد استخدامه، وFlutter mobile يحفظ عبر منتقي ملفات النظام مع حالات انتظار/فشل وإلغاء الحفظ. لا تغيير Backend أو Family. التحقق لهذه الدفعة: Web build ناجح وlint بلا أخطاء (3 تحذيرات سابقة)، Flutter analyze نظيف و25/25 tests؛ تنزيل الويب واختيار حفظ الموبايل اختبرا بملفات/mocks معزولة، لا جهاز موبايل فعلي.

- صور وفيديوهات المنشور تفتح داخل معرض موحد في Web/Flutter، يحافظ على ترتيب الوسائط ويبدأ بالملف المضغوط: previous/next وعدّاد، وأسهم لوحة المفاتيح وEscape في Web، وPageView بالسحب وInteractiveViewer لتكبير الصور في Flutter. الفيديو يعمل داخل المعرض بطلب المستخدم، ويُزال/يُحرر المشغل عند مغادرة الفيديو أو إغلاق المعرض؛ فتح المعرض يوقف فيديوهات الويب inline. القراءة عبر نفس endpoint المصادق عليه، دون public URLs أو token في URL. هذا يحل محل المعرض الأول الذي اقتصر على الصور.

- زر اختيار وسائط المنشور في Schools Web أصبح عنصرًا مصممًا ثنائي اللغة بدل واجهة file input الأصلية المعتمدة على لغة المتصفح؛ يعرض حالة/عدد الملفات محليًا وأسماء الملفات ومعايناتها، مع إعادة ضبط الاختيار حتى بعد رفض الملف لإتاحة إعادة اختياره.

## توسيع إشعارات تشغيل المدرسة

- نُفذت أحداث إلغاء إسناد القسم/مادة الصف/الفصل/الحصة، وتغيير وقت الحصة أو مكانها، وتكليف/إنهاء رئاسة القسم وتنسيق المادة. تبديل المدرس بين الأساسي والاحتياطي داخل الحصة لا يولد إشعار إلغاء كاملًا كاذبًا. العضوية ورئاسة القسم والصلاحيات التقنية علاقات مستقلة.
- اعتماد الخطط وإرسالها ونشرها وأرشفتها يولد إشعارًا للمسؤول المؤهل فعليًا ضمن نطاق API؛ رئيس القسم المؤهل للمراجعة، والمدير بديل عند غيابه، والمنشئ/المرسل للتغييرات على خطته، ومدرسو المادة والفصول عند النشر. أضيف `POST teaching-plans/{id}/return-for-edit` بسبب إلزامي حتى 1000 حرف، يعيد Submitted إلى Draft ويحفظ السبب في audit. التفاصيل تعرض آخر سبب إعادة، وWeb/Flutter يتيحان المراجعة والإعادة وتعديل تفاصيل المسودة وإعادة إرسالها من رابط الإشعار. تعارض الحفظ يرجع 409 بدل إظهار نجاح زائف؛ RowVersion/xmin الحالي يظل حماية التزامن.
- تغيير «تحتاج متابعة» للملاحظة يخطر صاحبها والرؤساء المؤهلين دون اسم الطالب أو نص الملاحظة في الإشعار. نشر/إلغاء النشاط وإعادة فتح تقييمه يخطر المدرسين المخولين والمدير. الإضافة المباشرة للطالب أو قبول طلبه يولد ملخصًا واحدًا لقائمة الفصل لكل مدرس/يوم بتوقيت المدرسة، ويفتح القائمة الحالية. طلب التقديم الجديد وتغيير حالته/قبوله يخطر مسؤولي `SchoolNotifications:AdmissionsRecipients:{schoolCode}` إن ضُبطوا مع صلاحيات view/manage، وإلا المدير المؤهل.
- الإشعار ثنائي اللغة ومحفوظ مع عملية العمل في نفس SaveChanges؛ `EventKey` اختياري وفهرس فريد للمستلم/الحدث يمنع التكرار ويحافظ على السجلات القديمة ذات المفتاح null. تصادم ملخص الفصل المتزامن يعاد حفظه بعد حذف الإشعار المكرر من التتبع فقط، دون تجاهل أي قيد آخر أو فقد عملية تسجيل الطالب.
- خدمة `SchoolOperationReminderService` تعمل كل خمس دقائق فقط على قائمة `SchoolNotifications:SchoolCodes` الصريحة؛ الفارغة تعطّلها. تذكير بعد 24 ساعة من آخر تقدم/إعادة فتح، وتصعيد بعد 48 ساعة، لتقييم حصة أعيد فتحه ولم يعتمد، ونشاط سابق ناقص التسجيل/الدرجة، ورصد اختبار مفتوح لم يرسل للاعتماد. فحص الحالات الحالية والصلاحيات، منع التكرار لكل دورة حالية، ودفعات keyset محدودة الذاكرة (حتى 1000 سجل لكل نوع/مستوى في المرور الواحد). إشعارات المراحل السابقة تبقى على `ExamWorkflow:SchoolCodes` وخدمتها المستقلة.
- Web وFlutter يفتحان الخطة/النشاط/طلب التقديم الفعلي من الإشعار؛ الملاحظات والتقييم يفتحان تاريخ الحصة وخانتها، والرصد يفتح اختبارات الفصل المخول. إلغاء الصلاحية يعرض خطأ محليًا ولا يمنح الإشعار نفسه حق الوصول. قراءة الإشعار لا تنجز المهمة.
- migrations `20261004205137_AddSchoolNotificationEventKeys` PostgreSQL و`20261004205239_AddSchoolNotificationEventKeys` SQL Server جاهزة ولم تُطبق على مدرسة فعلية. يلزم تطبيقها عبر Action التحديث المركزي، وإعادة تشغيل API ونشر الواجهتين وضبط قائمة التذكير قبل اختبار التشغيل.
- حدود التنفيذ: لا Push/Realtime جديد ولا Family. لم تُخترع عمليات نقل/انسحاب الطلاب أو تعديل موعد النشاط المنشور (غير متاحة حاليًا)، ولا إسناد متابعة الملاحظة لشخص (الحقل الحالي boolean فقط). تذكير الحضور التاريخي مؤجل إلى إتاحة شاشة تصحيح قابلة للتنفيذ؛ الشاشة الحالية مقيدة بالحصة/اليوم الجاري. لا تذكير بتقييم اختياري لم يبدأ.

## تسليم مراحل الاختبارات وإشعارات المدرسة

- نُفذ مسار اختياري صريح للسلسلة في Schools API وWeb وFlutter: تجهيز الجدول، اللجان عند الحاجة، مراجعة كل ورقة بالقسم بالتوازي إذا طلبتها السياسة، اعتماد المدرسة إذا طلبته السياسة، ثم مسؤول النشر. لا تسلم المرحلة التالية عند حفظ المسودة، بل عند إتمام المرحلة صراحةً؛ تظل قيود النشر المباشر القديمة سارية للسلاسل دون مسار.
- لكل مرحلة مسؤول مؤهل في نطاق المادة/الفصول وصلاحيتها، وبديل ومشرف وموعد إنجاز اختياريون. توجد افتراضيات للمسؤولين لكل سياسة، تحفظ مع policy snapshot للاختبارات الجديدة فقط، وتظل قابلة للتجاوز لكل اختبار مع إعادة التحقق من النطاق.
- مركز الاختبارات يضم «مهامي» بصفحات وتحميل بالتمرير، و«مراحل الاختبار» على الكارت، و«مسؤولو المراحل» في السياسات. إشعار ExamWorkflow يفتح أحدث حالة للمسار في الواجهتين؛ قراءة الإشعار لا تنجز المهمة. الإرجاع بسبب يوقف المهام ويعيد المراجعة، ويظهر الاختبار المعاد في مهام منشئه.
- تحفظ المرحلة والإشعار الثنائي اللغة وOutbox ذريًا مع Revision للتزامن ومفتاح فريد للحدث. مراجعات الأوراق كلها مطلوبة قبل المرحلة التالية، ومسؤول النشر المحدد وحده يستطيع النشر بعد اكتمال المسار. تغيير الموعد قبل النشر يبطل الاعتمادات ويحتاج إعادة الإرسال؛ الإلغاء والنشر وتغيير الموعد يخطرون المسؤولين ومدرسي المواد والفصول المستهدفة والمراقبين المخولين.
- خدمة التذكير تفحص المدارس الموجودة صراحةً في إعداد `ExamWorkflow:SchoolCodes` كل دقيقة؛ تنشئ تذكيرًا واحدًا عند التأخر وتصعيدًا للمشرف بعد 24 ساعة، مع إعادة فحص أهلية المسؤول والبديل. القائمة الفارغة لا تفحص أي مدرسة. Outbox مُجهز فقط لقنوات Push/Realtime المستقبلية؛ لا يوجد ناقل Push جديد في هذا التنفيذ، ولا إشعار Family أو جهة تعليمية خارجية.
- migrations `AddExamWorkflowNotifications` جاهزة لـPostgreSQL وSQL Server ولم تُطبق على قاعدة فعلية. يلزم تطبيقها وإعادة تشغيل الخدمة وضبط قائمة المدارس للتذكير وإجراء smoke test فعلي قبل اعتبار الإطلاق متحققًا.

- التقرير المنسق المقابل محفوظ في `docs/reports/Mdaresna-UltimateSchools-Academic-Gap-Analysis-AR.docx`.
- النطاق المستقبلي المتفق عليه للنظام المالي والإدارة الداخلية للموظفين والموارد وFamily App محفوظ في `docs/reports/POST_ACADEMIC_MODULES_REFERENCE.md`.
- لا تُخزن بيانات دخول المنصة المرجعية أو أي أسرار داخل ملفات المشروع.

## حدود الوحدات المستقبلية

- بعد اكتمال النظام الأكاديمي، تُنفذ داخل نطاق المدرسة وحدات النظام المالي وإدارة الموظفين والموارد، وتظل بياناتها التشغيلية داخل قاعدة المدرسة.
- Family App هو قناة الطالب وولي الأمر للتقديم وربط الأسرة والمواعيد والمقابلات والمحاضرات الأونلاين والتواصل وعرض البيانات الأكاديمية والمالية المسموح بها.
- Family App لا يملك قواعد القبول أو القيد أو الحضور أو الدرجات أو الرسوم؛ تظل قواعد العمل ومصدر الحقيقة في Schools Backend والوحدات المركزية المناسبة للهوية والإشعارات.

## التطبيقات

- `Mdaresna`: Backend ويحتوي Platform API وPlatform Worker وSchools API والعقود المشتركة.
- `Mdaresna_Platform_Web`: تطبيق إدارة المنصة باستخدام React.
- `Mdaresna_Platform`: تطبيق إدارة المنصة باستخدام Flutter.
- `Mdaresna_Schools_Web`: تطبيق المدارس باستخدام React.
- `Mdaresna_Schools`: تطبيق المدارس باستخدام Flutter.
- يعرض Platform API وSchools API واجهة Swagger في بيئة `Development` فقط. Swagger الخاص بالمدارس متاح دون جلسة لعرض العقد، ويحتوي تعريف Bearer لإدخال School access token عند تجربة endpoints المحمية؛ يظل Swagger غير مفعّل خارج Development.

## تعدد المدارس وقواعد البيانات

- كل مدرسة تمثل Tenant ولها قاعدة بيانات تشغيلية مستقلة حاليًا.
- Platform هو Control Plane ويحتفظ ببيانات المدرسة وموقع قاعدة بياناتها داخل `registry.school_database_endpoints`.
- لا تُخزن بيانات الاعتماد داخل السجل؛ يستخدم `CredentialSecretReference` للإشارة إلى مصدر أسرار خارجي.
- PostgreSQL هو المزود الافتراضي الحالي لقواعد المدارس.
- إنشاء مدرسة جديدة يشغل أحدث Schools migrations أثناء provisioning قبل تفعيل المدرسة.
- تحديث قواعد المدارس الموجودة يتم مركزيًا من Platform فقط، وليس أثناء تسجيل الدخول أو مع كل Request.

## دورة إنشاء المدرسة

1. المستخدم يرسل طلب إنشاء مدرسة من Schools Web أو Flutter.
2. Schools ينشر event إلى RabbitMQ.
3. Platform يستهلك الطلب، يتحقق من حساب المالك أو ينشئه، ويسجل المدرسة بحالة انتظار المراجعة.
4. مسؤول Platform يقبل المدرسة ويختار نوع الوحدة.
5. Platform ينشر أمر provisioning.
6. Schools API consumer ينشئ قاعدة PostgreSQL، يشغل migrations، يضيف معلومات المدرسة، وينشئ المستخدم المحلي للمالك بحالة انتظار التفعيل.
7. Schools يعيد نتيجة provisioning؛ Platform يسجل database endpoint ويفعّل المدرسة.
8. المالك يستلم رسالة باسم الدخول الكامل فقط، بدون OTP.

## هوية مستخدم المدرسة

- `Person`: الشخص داخل نطاق المدرسة، وقد يكون طالبًا أو مستخدمًا.
- `LocalUser`: شخص يستطيع تسجيل الدخول إلى تطبيق المدرسة مثل المالك أو المدير أو الموظف أو المدرس.
- بيانات الدخول محلية داخل قاعدة المدرسة وليست Platform credentials.
- صيغة الدخول: `username@schoolCode` مع كلمة مرور المدرسة المحلية.
- التفعيل لأول مرة: يطلب المستخدم OTP بعد إدخال اسم الدخول، ثم يرسل OTP وكلمة المرور الجديدة.
- OTP لا يُنشأ ولا يُرسل أثناء provisioning.
- دور `School Admin` والصلاحيات المحلية والأدوار وعلاقات المستخدمين موجودة على مستوى قاعدة المدرسة.
- Schools Web يحتفظ بجلسة تسجيل الدخول ويستخدم access token لقراءة بيانات المدرسة المحلية.
- Platform وSchools يدعمان «تذكرني» في Web وFlutter. الـaccess token قصير العمر ويُجدد قبل انتهائه بدقيقة باستخدام refresh token دوّار؛ يستعيد العميل الجلسة عند التشغيل أو يعيد شاشة الدخول إذا انتهت أو أُلغيت.
- زر تسجيل الدخول في Schools Web وFlutter يعرض حالة انتظار مترجمة ويمنع الإرسال المتكرر حتى اكتمال الطلب، وكذلك إجراءات التفعيل.
- جلسة «تذكرني» صالحة حتى 30 يومًا، والجلسة غير الدائمة حتى يوم واحد. Web يستخدم `localStorage` للدائمة و`sessionStorage` لغير الدائمة، بينما Flutter يحفظ الجلسة الدائمة فقط في التخزين الآمن للنظام عبر `flutter_secure_storage` ولا يحفظ كلمة المرور.
- تسجيل الخروج يلغي refresh token في الـBackend ويمسح التخزين المحلي. Platform يستخدم جدول `identity.sessions` الموجود، وSchools يستخدم `local_user_sessions` داخل قاعدة المدرسة، لذلك لم تُضف migrations لهذه الميزة.
- يلغي Platform فحص JWT بهدوء إذا أُلغي طلب HTTP نفسه أثناء فتح اتصال قاعدة البيانات، ولا يصنف هذا كتوكن غير صالح؛ تظل أعطال PostgreSQL الحقيقية غير مخفية.
- `GET /api/schools/v1/school-profile` يعيد بيانات `SchoolInformation` للمدرسة المحددة من claim كود المدرسة.
- لوحة Schools Web تعرض اسم المدرسة الفعلي. صفحة تعريف المدرسة في Schools Web وFlutter تعرض غلافًا مختارًا من المعرض وشعارًا مستقلًا، ووصفًا مختصرًا ونبذة ورؤية ورسالة وأهدافًا مرتبة بالعربية والإنجليزية ووسائل التواصل. تدعم التحرير والمعاينة وإدارة الصور وترتيبها وتعليقاتها؛ الغلاف يظهر كاملًا ومتمركزًا باستخدام `contain` دون قص أو تشويه، وتظهر خلفية هادئة في المساحة المتبقية عند اختلاف الأبعاد. القراءة للمستخدم المدرسي المسجل والتعديل لصلاحية `school.profile.manage` الممنوحة لمدير المدرسة.
- `SchoolPresentation` مستقل عن هوية المدرسة الأساسية ويحمل `Revision` للتزامن المتفائل. الصور روابط `SchoolProfileImage` typed إلى Document Core، بحد 30 صورة للمعرض وشعار مستقل، و8MB للصورة بصيغ PNG/JPEG/WebP حسب توقيع المحتوى. إزالة الصورة أو استبدال الشعار تحفظ المستند الأصلي وتدقيقه، ومحتوى الصور يُقرأ بمصادقة المدرسة فقط. migrations هي PostgreSQL `20261002121024_AddSchoolPresentation` وSQL Server `20261002121052_AddSchoolPresentation`، ولم تُطبّق على قواعد المدارس القائمة خلال التنفيذ. لا يوجد عرض عام أو Family لهذه الصفحة حاليًا؛ فحص malware المركزي لا يزال مؤجلًا.
- قائمتا الحساب والإشعارات في Schools Web تتبعان نفس نمط Platform Web؛ الحساب يحتوي هوية المستخدم والأدوار واللغة وتسجيل الخروج ومدخل «تكليفاتي داخل المدرسة»، والإشعارات متصلة بـSchool Notifications API وتعرض العداد وحالات القراءة والروابط السياقية.
- إعدادات Schools Web مقسمة إلى بيانات شخصية وأدوار؛ الملف الشخصي وتخزين الصورة محليان داخل قاعدة المدرسة، وإدارة الأدوار محكومة بصلاحيتي `school.roles.view` و`school.roles.manage`.
- البيانات الشخصية في Schools Web تجلب الهاتف الرئيسي مباشرة من Identity عبر Platform internal API، وتدمجه مع الهاتف والبريد والعنوان الإضافيين المخزنين في `school.person_contacts`؛ الهاتف الرئيسي يظهر للقراءة فقط ولا تستخدم الجهات الإضافية لتسجيل الدخول.
- تبويبا «المعلمين» و«الموظفين» موجودان داخل الإعدادات لإدارة الحسابات والأدوار والحالات ونطاق مواد المعلم. العرض والإدارة محكومان بصلاحيتي `school.users.view` و`school.users.manage`.
- Schools Web يعرض أيضًا شاشتين تشغيليتين مستقلتين في القائمة الرئيسية بلا إضافة أو تعديل أو إيقاف أو حذف للحساب. تعرضان الصورة والهوية والقسم والحالة، وتدعمان التصفية المستقلة بالقسم والاسم ورقم الهاتف؛ وتحتوي شاشة المعلمين على التفاصيل والجدول الأسبوعي، وتحتوي الشاشتان على تسجيل الغياب والإذن والإجازة يدويًا.
- شاشة «الفصول» التشغيلية موجودة في القائمة الجانبية على Web وFlutter. يرى `School Admin` كل الفصول النشطة، ويرى المدرس فقط الفصول المرتبطة به عبر إسناد مادة داخل الفصل؛ ويطبق Schools API هذا النطاق قبل إعادة البيانات. تعرض الشاشة المسار الأكاديمي والفترة والسعة والإشغال والغرفة والمواد المتاحة للمستخدم.
- نطاق بيانات الشاشتين مُطبق في Schools API: `School Admin` يرى كل المعلمين والموظفين؛ وغيره يرى نفسه والأعضاء الفعالين في الأقسام التي يقودها والأقسام التابعة لها فقط، مع بقاء RBAC شرطًا مستقلًا. نفس النطاق يحمي الصورة والتفاصيل والتعديل وتغيير الحالة والحذف ونطاق التدريس وجدول المعلم.
- تصفية المستخدمين تتم Server-side؛ تستخدم الإعدادات البحث العام والحالة والدور، بينما تستخدم الشاشات التشغيلية القسم والاسم والهاتف، وتدخل كل الفلاتر في الإجمالي والـpagination.
- الحساب الحالي لا يمكن تعديله أو تعطيله أو حذفه من شاشة إدارة المستخدمين؛ تعديلات بياناته الشخصية تتم من تبويب البيانات الشخصية.
- يجب أن يوجد دائمًا موظف `Employee` فعال واحد على الأقل يحمل دور `School Admin`؛ تمنع الـAPI إزالة دوره أو تحويله إلى مدرس أو تعطيله أو حذفه إن كان الأخير.
- إنشاء مدرس أو موظف يبدأ بحل رقم الهاتف الرئيسي داخل Identity المركزية؛ إن لم يوجد الحساب يُنشأ، ثم يُنشأ `Person` و`LocalUser` داخل قاعدة المدرسة بحالة `PendingActivation` وتُرسل رسالة باسم الدخول الكامل `username@schoolCode`.
- مسار OTP وتعيين كلمة المرور لأول مرة متاح لكل مستخدم مدرسة في حالة انتظار التفعيل، وليس مقصورًا على مالك المدرسة؛ وبعد نجاحه يؤكد Schools للـPlatform أن الهاتف الرئيسي تم التحقق منه لتفعيل Identity account المعلق.
- صور مستخدمي المدرسة محفوظة في `school.person_profile_images` ومقيدة بصيغ JPEG/PNG/WebP وحجم 2 MB.
- المستخدم الذي لديه صورة يعرضها جدول المستخدمين عبر endpoint محمي بصلاحية `school.users.view`، مع fallback لأيقونة المستخدم.

## الطلاب وطلبات التقديم

- الـPlatform هو مصدر كود الطالب العالمي: يحتفظ بـ`GlobalStudentRegistry` ويصدر `GlobalStudentId` وكود `STU-*` فريدًا عبر internal API محمية. لا يحتفظ بقيد الطالب أو عضويته في مدرسة.
- كل قاعدة مدرسة تحتفظ بملف الطالب المحلي ونسخة مفهرسة من الهوية والكود العالمي، وأولياء الأمور، والقيود الدراسية، وطلبات التقديم. يرتبط الطالب بـ`Person` محلي واحد وفريد ويمكن ربط أكثر من ولي أمر به مع أساسي واحد إلزامي.
- تدعم المدرسة مسارين: تسجيل طالب مقيد مباشرة داخل فصل، أو إنشاء طلب تقديم يدوي بمصدر `SchoolDesk` ثم قبوله لاحقًا؛ القبول ينشئ الطالب والقيد ويربطهما بالطلب، ويخصص الكود العالمي عند الحاجة.
- شاشتا Schools Web وSchools Flutter تعرضان تبويبي «طلاب المدرسة» و«الطلبات المقدمة» بصلاحيات مستقلة. البحث Server-side بالعام ونوع التعليم والمرحلة والصف والاسم والكود وتاريخ الميلاد؛ يضيف الطلاب الفصل والحالة، وتضيف الطلبات الحالة والمصدر ونطاق تاريخ التقديم دون فلتر فصل قبل القبول. تعرض Schools Web هذه الحقول داخل لوحة عوامل تصفية collapsible مغلقة افتراضيًا ومتسقة مع Platform Web.
- يملك كل سجل طالب Action لعرض التفاصيل في Web وFlutter؛ يعرض البيانات الأساسية والرسمية، جميع أولياء الأمور وخصائص كل علاقة، وسجل القيود الدراسية التاريخي كاملًا.
- الصلاحيات هي `school.students.view/manage` و`school.admissions.view/manage`، ويحصل عليها `School Admin` من seed قاعدة المدرسة.
- migrations الحالية: Platform SQL Server `20260925191826_AddGlobalStudentRegistry` وPostgreSQL `20260925191837_AddGlobalStudentRegistry`؛ Schools PostgreSQL `20260925193625_AddStudentCoreAdmissions` وSQL Server `20260925193637_AddStudentCoreAdmissions`.

## تحديث قواعد بيانات المدارس

- الصلاحية: `platform.schools.migrations.execute`.
- يوجد Action لمدرسة واحدة وAction لكل المدارس الفعالة في Platform Web وPlatform Flutter.
- Platform API يسجل العملية كـ`Pending` ويكتب الأمر في Outbox ثم يرجع HTTP 202.
- Platform Worker ينشر الأمر إلى RabbitMQ.
- Schools migration consumer يتحقق من tenant/database target ويشغل `Database.MigrateAsync()`.
- النتيجة تعود إلى Platform Worker ويتم تحديث `MigrationStatus`, `SchemaVersion`, operation id، التواريخ، وآخر خطأ.
- الحالات الحالية: `NeverRun`, `Pending`, `Succeeded`, `Failed`.
- إذا كان RabbitMQ أو consumer متوقفًا تبقى الرسالة في Outbox/Queue وتُستكمل بعد عودة الخدمة.
- يلزم تشغيل Platform Worker لنشر أوامر Outbox واستهلاك نتيجة migration؛ تشغيل Platform API وSchools API وحدهما غير كافٍ.
- Platform Web يعرض عدد عمليات تحديث الكل التي دخلت الطابور فعليًا، ويحذر إذا كان العدد صفرًا بسبب عدم وجود مدارس مؤهلة أو وجود عملية معلقة، ويعرض رسالة واضحة للعملية الفردية الجارية.

## الإعدادات المدرسية

- الهيكل التنظيمي الموحد منفذ في Schools API وSchools Web وSchools Flutter: قسم بنوع `Academic` أو `Administrative` ونطاق على مستوى المدرسة أو فرع، مع شجرة أقسام اختيارية وترتيب وحالة تشغيل وsoft delete واستعادة.
- عضوية القسم مؤرخة وتسمح بعضويات ثانوية مع قسم أساسي واحد فقط لكل مستخدم. رئاسة القسم علاقة مؤرخة منفصلة، ويجب أن يكون الرئيس عضوًا فعالًا داخل القسم.
- القسم التعليمي يمكن ربطه بعدة مواد، ولكل مادة منسق مع نطاق اختياري لنوع تعليم ومرحلة؛ المنسق يجب أن يكون مدرسًا وعضوًا بالقسم. القسم الإداري لا يقبل المواد أو المنسقين، لكن نوع القسم يوجه مرشحي الواجهة ولا يمنع الاستثناءات التنظيمية في العضوية.
- الهيكل التنظيمي مستقل عن RBAC ولا تمنح العضوية أو الرئاسة صلاحيات تقنية تلقائيًا. الصلاحيات هي `school.departments.view/manage/delete/restore` ويحصل عليها `School Admin` من seed البيانات.
- صفحة الإعداد الأكاديمي في Schools Web تعرض الهيكلة الأكاديمية والصفوف الدراسية والمواد والمناهج وجدول الحصص داخل Accordion أحادي الفتح؛ أول قسم مفتوح افتراضيًا، وفتح قسم يغلق السابق، ولا تُحمّل بيانات القسم المقفول حتى فتحه.
- الهيكلة المادية منفذة في Schools API وSchools Web وSchools Flutter، وتعرض الإعدادات حسب الاعتماد: فرع ← مبنى ← دور ← أنواع الغرف ← قدرات الغرف ← الغرف؛ ويمكن للغرفة امتلاك عدة قدرات تسمح مثلًا لمعمل واحد بدعم الكيمياء والفيزياء.
- الهيكلة المادية تدعم CRUD، التفعيل والإيقاف، soft delete، سلة المحذوفات والاستعادة، وتمنع حذف الأصل قبل نقل أو حذف الأبناء.
- الصلاحيات: `school.facilities.view`, `school.facilities.manage`, `school.facilities.delete`, `school.facilities.restore`، ويحصل عليها `School Admin` من seed البيانات.
- الهيكلة الأكاديمية منفذة في Schools API وSchools Web وSchools Flutter: نوع تعليم ← تعريف عام دراسي ← عام للبرنامج ← تيرمات ← فترات، مع CRUD والتفعيل والإيقاف وsoft delete والاستعادة.
- التنظيم الدراسي داخل نوع التعليم منفذ كالتالي: مرحلة دراسية ← مسار اختياري ← صف دراسي، ثم فتح الصف داخل عام البرنامج وإنشاء فصل دراسي واحد أو أكثر له. تشغيل الصف يحفظ فقط مرجعي العام والصف والسعة والحالة؛ الكود والاسمان يولدهم Schools API تلقائيًا، والمرحلة والمسار مجرد فلاتر اختيار في الواجهة.
- الفصل الدراسي كيان سنوي مستقل عن الغرفة المادية؛ نموذج إنشائه يطلب تشغيل الصف والسعة والفترة فقط، ويولد Schools API الكود والاسم التسلسلي تلقائيًا. ربط الفصل بالغرفة يتم من خلال إسناد مؤرخ اختياري الساعات، مع التحقق أن نوع الغرفة مخصص للفصول وأنها قابلة للجدولة وسعتها كافية ولا يوجد تعارض زمني.

- تبويب «الأنشطة» داخل «فتح الفصل» منفذ في Schools API وSchools Web وSchools Flutter. يدعم النشاط نطاقًا عامًا أو مادة يدرسها المستخدم، وأنواعًا تشغيلية متعددة، وتاريخًا ووقتًا ومكانًا اختياريين، وتقييمًا اختياريًا بإجمالي درجة، وجمهور كل الفصل أو طلابًا محددين. الإنشاء والتعديل يتمان في ثلاث خطوات، وتتوفر قائمة بفلاتر النطاق والمادة والنوع والحالة والتاريخ ثم عرض تفاصيل مستقل. يعيد محرر المسودة التحقق من المواد والقيود الفعالة ويستبعد القيم القديمة مع تنبيه واضح بدل حفظ مرجع غير صالح.
- دورة نشاط الفصل هي `Draft → Published → Completed` أو `Cancelled`: المسودة وحدها قابلة للتعديل أو الحذف، والنشر ينشئ snapshot من القيود الفعالة، والنشاط العام لكل الفصل ينبه إلى الطلاب المضافين لاحقًا ويتيح مزامنتهم إضافةً فقط. فشل النشر بعد نجاح الإنشاء يبقي نفس المسودة لإعادة المحاولة بدل إنشاء نسخة مكررة.
- مشاركة الطالب منفصلة عن درجته بقيم `NotRecorded/Participated/DidNotParticipate/Excused` مع ملاحظة اختيارية. يمكن حفظ التقدم جزئيًا، ولا يكتمل النشاط قبل تسجيل حالة الجميع وإدخال درجة كل مشارك عندما يكون النشاط مُقيّمًا؛ ويمكن إعادة فتح المكتمل بسبب إلزامي مع الاحتفاظ بسجل التدقيق.
- جداول `class_activities/class_activity_audience_students/class_activity_participants/class_activity_audits` تحفظ البيانات والجمهور والـsnapshot والتاريخ التشغيلي. الصلاحيات هي `school.activities.view/manage/publish/grade/reopen`، والمigrations هي PostgreSQL `20260929151727_AddSchoolClassActivities` وSQL Server `20260929151742_AddSchoolClassActivities`.
- أخطاء Schools API تظل معرفة بأكواد مستقرة؛ Schools Web وSchools Flutter يترجمان الأكواد وفق اللغة النشطة ويستخدمان fallback مترجمًا بدل إظهار النص الإنجليزي القادم من الخادم. أخطاء تشغيل المواد تميز تحديدًا بين عدم إسناد الخطة للعام واختلاف الخطة أو الصف وعدم التفعيل.
- كيانات الهيكلة المادية تدعم حالتي التشغيل `Active/Inactive` بالإضافة إلى soft delete قابل للاستعادة؛ السجلات المحذوفة لا تظهر افتراضيًا ولا تُحذف ماديًا.

## الإشعارات

- ربط المدرس بالقسم أو مادة صف سنوية أو مادة داخل فصل أو حصة أسبوعية ينشئ إشعارًا عربيًا/إنجليزيًا داخل نفس `SaveChanges` الذي يحفظ الإسناد. لا يرسل الحفظ المتكرر دون إضافة إشعارًا آخر؛ إعادة الإسناد بعد الإزالة تعد إضافة جديدة. تغيير وقت الحصة يخطر مدرسيها الحاليين كذلك. لا تنشأ إشعارات بأثر رجعي للإسنادات الموجودة.
- النص يوضح القسم وفترة العضوية والأساسي، أو المادة والصف ونوع التعليم والعام والفصل عند وجوده، أو يوم الحصة والخانة ووقت المدرسة ودور المدرس. ترشيح البديل الاحتياطي صريح ولا يعامل كتغطية فعلية.
- إشعار `TeacherAssignment` يفتح القسم المناسب من صفحة «تكليفاتي داخل المدرسة» في Web وFlutter ويبرز الربط المحدد ويعرض حالته الحالية؛ إذا أزيل الربط تظهر رسالة عدم إتاحته بدل اعتماد محتوى إشعار قديم. الصفحة تقرأ إسنادات الحساب الحالي فقط من endpoint self-service دون منح صلاحيات إدارة أو كشف إسنادات الآخرين. المدخل المستقل في قائمة حساب Web وصفحة إشعارات Flutter.
- Schools API يحفظ إشعارات المستخدم المدرسية داخل قاعدة المدرسة ويعيد آخر 50 إشعارًا مع عدد غير المقروء، ويدعم تعليم إشعار واحد أو الجميع كمقروء.
- إسناد تغطية حصة يرسل للبديل إشعارًا عربيًا وإنجليزيًا بالمادة والفصل والتاريخ والوقت واسم المدرس الغائب؛ تغيير التكليف أو إلغاؤه أو حذف الغياب يرسل إشعار إلغاء للبديل السابق.
- Schools Web يعرض العداد والقائمة السريعة وصفحة الإشعارات، وSchools Flutter يعرض صفحة الإشعارات والعداد وحالات القراءة. توصيل Push عبر Firebase/Realtime لم ينفذ بعد؛ التخزين داخل التطبيق هو مصدر الحقيقة الحالي.
- الإشعارات التي تحمل refresh signal تحدث حالة التطبيق فور وصولها في الواجهة الأمامية.
- العداد يتجدد من listener الاستقبال بدل الاعتماد على فتح قائمة الإشعارات.
- Web يطلب notification permission عند بدء التطبيق ويدعم browser notifications.
- إشعار تفعيل مستخدم Platform الجديد يوجه إلى قائمة المستخدمين ولا يجبر التطبيق على refresh كامل.

## إعدادات النشر الحساسة

- توجد Dockerfiles مستقلة لـPlatform API وPlatform Web وSchools API وSchools Web وPlatform Worker، مع `docker-compose.yml` موحد يضيف PostgreSQL وRabbitMQ وhealth checks وruntime environment configuration لتطبيقي الويب. دليل التشغيل في `docs/deployment/DOCKER_DEPLOYMENT.md`.
- لا تستخدم `dotnet user-secrets` داخل Docker أو بيئة الإنتاج.
- الأسرار تُمرر كـenvironment variables أو من secret manager.
- `PlatformSms__EncryptionKey` يجب أن تكون القيمة نفسها في Platform API وPlatform Worker.
- إعدادات PostgreSQL وRabbitMQ وFirebase وSMS وInternal API key يجب إدراجها في خطة النشر بدون تسجيل قيمها في المستودع.

## خطط التدريس والمستندات

- تدعم المدرسة خطط `Yearly/Term/Monthly/Weekly/Daily`: السنوية والتيرم على تشغيل الصف والمادة، والشهرية والأسبوعية واليومية على فصل واحد أو عدة فصول من تشغيل الصف نفسه.
- يولد Schools API اسم الخطة من النوع والفترة والتيرم والمادة، وتمر المسودة بحالات `Submitted/Approved/Published/Archived` مع منع نشر نطاق متداخل للمادة والنوع والفترة نفسيهما.
- Schools Web يدير السنوية والتيرم من الإعداد الأكاديمي، والثلاث الأخرى من قائمة الفصول باختيار متعدد أو من كارت الفصل. محرر Web منظم إلى نطاق ومحتوى ومرفقات، مع اختيار مرئي لنوع الخطة والفصول، حقول موحدة، فترة واضحة، ومنطقة رفع ملفات مخصصة. Schools Flutter يدعم إنشاء الأنواع واختيار الفصول ورفع المرفقات من شاشة الفصول.
- الفترة التشغيلية ليست إدخالًا حرًا في Schools Web: الشهرية تختار شهرًا من أشهر التيرم، والأسبوعية تختار شهرًا ثم أسبوعًا محسوبًا من بداية التيرم، واليومية تختار تاريخًا واحدًا يبدأ افتراضيًا بتاريخ المدرسة المحلي. يتحقق Schools API من تطابق الفترة الشهرية والأسبوعية مع التقسيم نفسه.
- Document Core المدرسي يخزن metadata والنسخ والبصمة وحالة التحقق داخل قاعدة المدرسة، ويحفظ المحتوى خارج PostgreSQL عبر `ISchoolDocumentStorage`. المزود الحالي filesystem قابل للاستبدال بـS3/MinIO، والمفاتيح معزولة تحت `schools/{schoolCode}`.
- ربط المرفقات بالخطط typed عبر `teaching_plan_documents` وليس بمرجع polymorphic. تحتفظ الخطة بـ`SourceAuthority/SourceReference` لتكامل مكتبة محتوى Platform مستقبلًا دون نقل الملفات الخاصة خارج قاعدة المدرسة.
- migrations: PostgreSQL `20260930203507_AddTeachingPlansAndDocumentCore` وSQL Server `20260930205617_AddTeachingPlansAndDocumentCore`.

## تحميل سجلات التشغيل

- قوائم الواجبات وأنشطة الفصل واختبارات الفصل ومركز الاختبارات تستخدم Server-side pagination بحجم افتراضي `20` وحد أقصى `100` وترتيب ثابت، وتحمّل Schools Web وSchools Flutter الصفحة التالية تلقائيًا عند الاقتراب من نهاية التمرير مع منع تكرار العناصر.
- قوائم الطلاب اللازمة للحضور والرصد والتقييم الجماعي لا تدخل في هذا التقسيم؛ تبقى كاملة حتى لا ينتج حفظ جزئي غير مقصود.
- مركز الاختبارات وتبويب اختبارات الفصل في Schools Web وSchools Flutter يعرضان Accordion مستقلًا لكل نوع `Weekly/Monthly/MidTerm/TermFinal/YearFinal/Other`. يمكن إغلاق الجميع، ولا يفتح أكثر من نوع في الوقت نفسه. يحمل كل قسم صفحاته عند فتحه فقط، وتأتي أعداده والإجماليات من summary Server-side ضمن نطاق الشاشة أو الفصل لا من العناصر المحملة جزئيًا.
