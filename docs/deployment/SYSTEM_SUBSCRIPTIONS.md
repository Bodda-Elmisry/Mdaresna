# تشغيل الأنظمة والباقات والسعات

## نسخ الفواتير داخل المدرسة — تحديث 2026-10-19

- Platform هو مرجع إصدار الفواتير وتسجيل السداد ومراجعته. Schools يحفظ نسخة قراءة محلية في `school.invoice_copies`، منفصلة عن خزائن المدرسة والتحصيلات الدراسية. النسخة تتضمن رقم الفاتورة وقيمتها وعملتها وبنود الأنظمة والباقات وحالة السداد وسجلات التحويل/المندوب، دون هويات الموظفين الداخلية أو ملاحظات مراجعة الدفع.
- `SchoolInvoiceSnapshotChangedV1` يخرج من Platform Outbox في نفس حفظ تغيير الفاتورة، وعند انتقال المدرسة إلىActive يرسل الفواتير السابقة أيضًا. لا ترسل فواتير التسجيل إلى مدرسة لم تجهز قاعدتها بعد. إعادة مزامنة أي عقد من Platform تعيد نسخ فواتير المدرسة بالإصدارات الحالية.
- المسار: exchange `mdaresna.platform-events`، routing key `mdaresna.schools.invoice.snapshot-changed`، queue `schools.invoices.v1` مع `.dead`. الناشر يعلن الربط قبل الإرسال. المستهلك يعمل بنفس `SchoolSubscriptions:ConsumerEnabled` وBrokerUri أو fallback إلى اتصال provisioning. تبقى سياسةAMQPS خارجDevelopment. لا تضف اتصالًا مباشرًا منSchools إلىPlatform لكل فتح فاتورة.
- المستهلك يتحقق من producer/schema/tenant/school وتطابق قاعدة المدرسة والمبالغ والبنود، ويحفظ تحديثًا متزايدRevision بمعاملة وقفل صف، ويتجاهل المكرر/الأقدم. لا يمكن تغيير شروط الفاتورة الصادرة بإصدار أعلى؛ التغير المسموح هنا هو السداد. تعاد محاولة الأخطاء المؤقتة؛ الرسائل غير الصالحة تذهب إلىdead. لا receipt خاصًا لنسخ الفواتير في هذه النسخة؛ راقب queue/dead وSyncedAtUtc المحلي.
- طبّق `AddSchoolInvoiceCopies` على قواعدSchools لكل مزود، ثم انشرSchools API وPlatform Worker وPlatform API، وبعدها الواجهة. لا migration جديدة لـPlatform. في تطويرحورس فقط طبقت مهاجرةPostgreSQL بعدbackup محلي وأعدت مزامنة الفاتورة القديمة؛ بقية المدارس لم تهاجر في هذا الطلب.
- API القراءة: `GET /api/schools/v1/subscription-invoices?page=1` بصلاحية `school.profile.manage`، ثلاثون سجلًا في الصفحة وhasMore، على قاعدة المدرسة منclaims فقط. لا endpoint لتعديل الفواتير فيSchools. الواجهة تعرض البطاقات والاستخدام والفواتير وتفاصيلها وزرطباعة يمكن منه حفظPDF عبرالمتصفح؛ ليست خدمةتوليدPDF علىالخادم.
- زر تهيئة الاستخدام لم يعد فيواجهةالمدرسة. عند وصول عقدStudent صالح لقاعدة بلا أيطلاب أوallocations، تهيأ سعة صفر تلقائيًا؛ إعادةالرسالةلاتعيدتصفيـرالاستخدام. قواعدالمدارس التي بهاطلاب تبقى بحاجةلمراجعة وتهيئة داخليةقبلتشغيلالحد؛ endpoint التهيئة القديم باقٍ للتوافق وبصلاحياته السابقة. لا يتغيرRequireEntitlement عالميًا من هذه العملية.

الحالة: تنفيذ محلي محدّث بتاريخ 2026-10-19 دون نشر إنتاجي. تغييرات قواعد التطوير المحددة موثقة فيCURRENT_STATE. راجع الخطة في `docs/implementation/SYSTEM_SUBSCRIPTIONS_AND_CAPACITY_TECHNICAL_PLAN.md`.

## القواعد المعتمدة

- التعاقد سنوي بسعة ثابتة. كل الأسعار والسعات وترتيب الباقات من Platform؛ لا أسعار تجارية ثابتة في الكود.
- المدرسة المرجعية بكل فروعها نطاق واحد. الطالب المفعّل وله قيد نشط في عام دراسي مفعّل يحتسب مرة واحدة. إيقاف الطالب يعيد المقعد؛ إعادة التفعيل تتحقق من المتاح. تغيير حالة العام يعيد مطابقة الاستخدام ذريًا؛ إعادة عام تضيف طلابًا فوق الحد تُرفض.
- الترقية بفرق قيمة الباقتين الأساسيتين، دون نسبة زمنية، مع الاحتفاظ بالإضافات وبنهاية السنة. فرق صفر يحتاج اعتمادًا مستقلًا؛ الفرق السالب مرفوض حتى توجد سياسة استرداد معتمدة.
- في التجديد تختار المدرسة عدد الإضافات المطلوب تجديده؛ يحاسب بسعر الإصدار المختار للتجديد. لا ترحيل آلي للإضافات المشتراة. الإتاحات الجديدة للعقود الجديدة والتجديدات فقط؛ الإضافات والترقية تحفظ إتاحات العقد الحالي.
- شراء إضافات داخل السنة بسعر الإضافة المثبت في العقد الحالي وحتى نهاية مدته؛ أرشفة الباقة لا تمنع إضافات عقد قائم. لم يُحسم تغيير هذا السعر أثناء السنة، ولذلك لا يعاد تسعير عقد قائم ضمنيًا.
- بعد الانتهاء قراءة فقط حتى التجديد، وتظل صلاحيات المستخدم ونطاق البيانات مطلوبين. الإيقاف يمنع الكتابة كذلك. لا مهلة مجانية أو تصدير جديد في هذه الدفعة.
- تجديد قبل نهاية العقد غير مدعوم بعد: الجدولة المبكرة تحتاج فترات مستقبلية منفصلة حتى لا يُستبدل العقد الساري. التجديد الحالي يبدأ من نهاية الفترة السابقة ولا يحرّكها تلقائيًا إلى يوم السداد المتأخر.
- تعريف كتالوج Employee/Cashbox لا ينفذ وظائف HR/Finance أو احتساب الموظفين والخزن؛ إتاحاتها المستقبلية مميزة في الكتالوج. مدرسو وموظفو التشغيل الأكاديمي لا يستهلكون مقاعد HR.

## المهاجرات والنشر

1. خذ نسخة احتياطية قابلة للاستعادة للمنصة وكل مدرسة pilot، وجرد الطلبات المالية ورسائل provisioning القديمة. لا تحوّل أرصدة الوحدات إلى مقاعد طلاب بمعامل مفترض.
2. طبّق مهاجرات Platform بحسب مزود القاعدة:
   - PostgreSQL: `20261015101320_AddSystemSubscriptionCatalog` ثم `20261015102011_AddSubscriptionCapabilitySnapshots` ثم `20261015104800_AddSubscriptionDeliveryReceipts` ثم `20261015112108_AddOfflineInvoicesAndRegistrationOffers`.
   - SQL Server: `20261015101526_AddSystemSubscriptionCatalog` ثم `20261015101918_AddSubscriptionCapabilitySnapshots` ثم `20261015104808_AddSubscriptionDeliveryReceipts` ثم `20261015112113_AddOfflineInvoicesAndRegistrationOffers`.
3. طبّق Schools: PostgreSQL `20261015101751_AddSchoolSubscriptions` أو SQL Server `20261015102500_AddSchoolSubscriptions`. لا يستخدم migration worker الحالي لاستهداف قواعد على hosts مختلفة دون إصلاح التوجيه الموثق سابقًا.
4. انشر Schools consumer المتوافق مع provisioning V1/V2 أولًا، ثم Platform API/Worker والواجهات Web/Flutter. الموافقات الجديدة بدون نوع وحدة وترسل V2؛ إعادة الرسائل القديمة المدفوعة تبقى متوافقة حتى التصريف. لا ترجع لمستهلك V1 وحده بينما توجد V2 معلقة.
5. فعّل `SCHOOL_SUBSCRIPTIONS_CONSUMER_ENABLED=true` بعد schema؛ يفعّل snapshots في Schools وreceipts في Platform Worker. احتفظ بـ`SCHOOL_SUBSCRIPTIONS_REQUIRE_ENTITLEMENT=false` فقط أثناء الترحيل. مفتاح `SCHOOL_SUBSCRIPTIONS_BLOCK_EXPIRED_READS=false` يطابق قرار القراءة بعد الانتهاء؛ لا تفعّله دون قرار منتج جديد.
6. اتصال RabbitMQ يأتي من secret source الحالي عبر `SchoolSubscriptions:BrokerUri` و`SchoolSubscriptionResults:BrokerUri`؛ AMQPS في الإنتاج وvhost مستقل لكل بيئة. لا connection strings أو مفاتيح في هذا المستند.

## إعداد الكتالوج والمدرسة

1. بصلاحية `platform.billing.manage` عرّف النظام وإتاحاته، ثم custom plan بسعة وسعر فرد وسعر إضافة وعملة وترتيب. انشر إصدار الباقة؛ تعديل الأسعار يولّد إصدارًا آخر ولا يعدّل تاريخ العقد.
2. المدرسة الجديدة تختار باقات الأنظمة أثناء طلبها من Schools. يحفظ السيرفر السعر والإصدار والإتاحات ويرسلV3؛ في Platform تظهر المدرسة المعلقة وفاتورة واحدة ببنود الاختيارات. من شاشة الفواتير أو تفاصيل المدرسة سجل كامل المبلغ فقط بتحويل أو كاش بمندوب؛ أدخل مرجع الإيصال وتاريخ الاستلام، ومع النقد اسم/كود المندوب. مسؤول آخر بصلاحية `platform.payments.approve` يراجع السداد وفق قاعدة منع المراجعة الذاتية القائمة. اعتماد الفاتورة وحده لا ينشئ قاعدة المدرسة؛ بعده اعتمد المدرسة ليبدأ الإنشاء والعقود السنوية والسعات. السنة الأولى تبدأ باعتماد المدرسة. الإيصال المرفوض يبقى محفوظًا ويمكن تسجيل محاولة مصححة.
   - للمدرسة القائمة: أعد عرض الاشتراك/الإضافة/الترقية/التجديد ثم «إصدار فاتورة»، وسجل التحصيل واعتمده من نفس شاشة الفواتير. العملية بلا مقابل تحتاج اعتمادًا مستقلًا، دون إيصال صفر. لا تستعمل بيع الوحدات القديم؛ الكتابة عليه410.
3. راقب حالة وصول الاشتراك في Platform. الاعتماد وحده لا يثبت الوصول. يظهر التأكيد فقط عند receipt بإصدار العقد الحالي. «إعادة المزامنة» تعيد snapshot مطلقة بنفس الإصدار عبر Outbox دون زيادة السعة أو الاستخدام.
4. في Schools افتح «الاشتراكات والسعات» بحساب يملك `school.profile.manage`. طابق العدد المتوقع مع الطلاب النشطين في الأعوام المفعّلة عبر كل الفروع؛ التهيئة تتطلب أيضًا `school.students.manage`.
5. أوقف طلبات تعديل الطلاب وتبديل الأعوام مؤقتًا أثناء قطع pilot، بما يشمل الطلبات الجارية، ثم أكد التهيئة بالعدد والإصدار المعروضين. لا تعطل الإتاحة الأمنية العامة لتحقيق هذا التوقف. التهيئة ترفض زيادة العدد عن السعة ولا توقف طلابًا تلقائيًا. الحد الحالي للتهيئة10,000 طالب؛ مدرسة أكبر تحتاج أداة baseline مجزأة قبل التفعيل.
6. بعد التهيئة تحقق من المستهلك والمتاح، وجرّب آخر مقعد، وإيقاف طالب ثم إعادة استخدام المقعد، وقبول طلب التحاق، وتغيير العام، والإضافات والترقية والتجديد والقراءة بعد الانتهاء. بعدها فعّل strict mode على المجموعة المهاجرة؛ لا تفعّله على replicas تخدم مدارس لم تهيأ بعد.

## ضمانات المزامنة وحدودها

- Platform مصدر العقد والحد والإتاحات. Schools مصدر الاستخدام؛ لا طلب Platform لكل تخصيص مقعد.
- snapshots ذات إصدار مطلق، وتكرارها أو وصول القديم لا يكرر المنح أو يخفض الإصدار. قفل SQL لنفس السعة يحمي التفعيل وتغيير الحد ومطابقة العام على PostgreSQL وSQL Server.
- قناة snapshots: exchange `mdaresna.platform-events`، queue `schools.subscriptions.v1`، نوع `mdaresna.schools.subscription.snapshot-changed`.
- قناة التأكيد: exchange `mdaresna.school-events`، queue `platform.subscriptions.applied.v1`، نوع `mdaresna.schools.subscription.applied`؛ queue لكل منهما مع لاحقة`.dead` للرسائل غير الصالحة.
- بعد حفظ SQL تنشر Schools receipt مع publisher confirm، ثم تقر باستلام الرسالة الأصلية. التعطل بين الحفظ والإقرار يعيد الرسالة وينشر التأكيد دون تكرار التعديل. الرسالة الأصلية الدائمة هي مسار إعادة المحاولة؛ لا يوجد مسح دوري لكل قواعد المدارس لإرسالACK.
- Platform يحفظ آخر إصدار مؤكد دون تعديل Version التجاري للعقد، فيستمر صلاح عرض قائم. الأحداث المشوهة/اختلاف النطاق إلى dead queue، وأعطال القاعدة أو الاتصال يعاد انتظارها. راقب تأخر Outbox وqueues وdead queues؛ لا إيقاف لحظي مضمون خلال تعطل broker.
- خفض السعة بالتجديد لا يحذف تخصيصات ولا سجلات طلاب. إن صار الاستخدام أعلى من الحد، تتوقف الزيادات حتى خفض الاستخدام أو زيادة السعة؛ يلزم مراجعة سياسة قبول هذا التخفيض قبل الإنتاج.
- أسماء الأكواد المدعومة ثابتة لربط التنفيذ، لكن تكوين النظام وأسعاره فيDB. الإتاحة لا تمنح دور مستخدم تلقائيًا.

## الترحيل والتراجع

بيع الوحدات الجديد وواجهة الاختيار أوقفا، لكن الجداول والسجل المالي ومستهلكو الرسائل القديمة باقون لحفظ التاريخ وتصريف العمليات السابقة. لا حذف schema أو mapping تلقائي لعقود حقيقية هنا. أكمل جرد ومطابقة pilot قبل حذف الكود والجداول المتقاعدة نهائيًا.

عند مشكلة pilot أوقف الكتابات أولًا، وافحص revision/Outbox/receipts والسعة. الرجوع المؤقت إلى transitional mode لا يصحح أعدادًا ولا يحذف عقدًا، ويجب أن يكون تغييرًا تشغيليًا مراقبًا. لا تسقط المهاجرات مع وجود عقود أو مدفوعات جديدة؛ استعد backup أو نفّذ إصلاحًا أماميًا بعد المطابقة.

متبقٍ قبل إعلان الترحيل مكتملًا: جرد وmapping للمدارس الفعلية، تجربة pilot واستعادة، نشر منسق، مراقبة الإنتاج، وإزالة المتبقي التاريخي من الوحدات بعد التصريف. كذلك التجديد المبكر، baseline الكبير، وسياسات HR/Cashbox والتخفيض ما زالت أعمالًا مستقلة.

## ترتيب نشر رحلة التسجيل والفواتير واختبارها

- بعد مهاجرة Platform، انشر Platform API وWorker أولًا مع `SchoolRegistrationConsumer:Enabled` ومصدر `SchoolRegistrationConsumer:BrokerUri` الحالي، وتحقق من إعلان queue `platform.school-registration-requested.v3` وربط `school.registration.requested.v3` على exchange `mdaresna.school-registry`. يحتفظ مستهلكV2 بطلباته السابقة؛ لا تحذف queues. الرسائل الفاسدة لها queue `.dead` مستقلة، والمحاولات العارضة تتبع سياسة إعادة الانتظار الحالية.
- ثم انشر Schools API وWeb/Flutter؛ يستعمل API `SchoolIdentity:PlatformBaseUrl` و`SchoolIdentity:InternalApiKey` من مصدر الأسرار القائم، المطابق لـ`InternalServices:ApiKey` على Platform. المفتاح لا يصل للمتصفح. لا تسجيل مقبول دون باقة منشورة؛ اختبر تعطل Platform وفشل النشر وإعادة المحاولة بنفس RequestId دون فاتورة ثانية.
- تسجيلV2 السابق لم يحتو اختيارات؛ الموافقة الجديدة تتطلب له عقدًا ساريًا وفاتورة مدفوعة معتمدة. راجع هذه الطلبات قبل القطع. إعادة provisioning لعقدV1 ذي UnitType تحفظ التوافق القديم؛ لا تحوّلها لبيع جديد.
- قبول staging: اختر نظامين، طابق السعر المجمد رغم تغيير الكتالوج، امنع الجزئي والتفعيل قبل الدفع، سجل النقد بمندوب ثم ارفضه وأعده بتحويل، اعتمد من حساب مراجع آخر ثم وافق على المدرسة. طابق فاتورة واحدة وسجل دفع واحد والعقود وOutbox ووصول السعة وإنشاء DB. جرّب تصحيح الإيصال، التكرار، تعطل Broker والهوية، والتفعيل بعد تأخير السداد. هذه تجربة نشر لازمة؛ اختبارات QA SQL والواجهات المحلية لا تثبت اكتمالها.
- `PlatformInvoice` يحفظ الحالة والنسخة، وبنود الفاتورة والإيصالات append-only في EF؛ تعديل الشروط أو حذف سجل مالي ليس مسارًا مدعومًا. ليس هنا تكامل مع منظومة ضريبية أو رفع صور إثبات الدفع.

## إضافات التعاقد الأول ورحلة التسجيل المرحلية — 2026-10-18

- التسجيل في Schools Web: الأنظمة والباقات، ثم الإضافات الاختيارية، ثم بيانات المدرسة. الاختيارات والأسعار من الكتالوج المنشور فقط. AdditionalQuantity اختياري في RegistrationPlanSelection وافتراضيه0؛ يثبت السيرفر السعر والكمية في نفس عرض New، ويضم الفاتورة لهما. العقود والسعات لا تطبق إلا بعد الاعتمادات القائمة.
- لا migration إضافية لهذه الدفعة؛ استعمل أعمدة العرض والعقد الموجودة. انشر Platform API ثم Schools API ثم Web، لأن نشر Web أولًا فوق API قديمة قد يجعل الكمية غير معروفة لها. Worker يجب أن يبقى متوافقًا مع تسجيلV3 كما سبق. Flutter القديم يرسل0 ولا يحتاج إصدارًا جديدًا للتوافق.
- تحقق staging: اختيار باقتين ثم إضافات لكل منهما، الرجوع وتغيير باقة، حفظ المدرسة، مطابقة فاتورة مجموع الباقات والإضافات بأسعار السيرفر، ثم السداد الكامل والتفعيل ووصول BaseCapacity/AddOnCapacity إلى Schools. اختبر إعادة نفس الطلب بلا تكرار ورفض تغيير الكمية بنفس RequestId، وتعطل الكتالوج ورفض الكميات السالبة أو غير الصحيحة. لا تفترض أن شاشة تأكيد الطلب تعني إنشاء قاعدة المدرسة بالفعل.
